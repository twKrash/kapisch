# KAPISCH 3.0 architecture design

Date: 2026-09-29
Status: **accepted architecture contract** (explicit user approval); implementation governed by the separately accepted plan.
Scope: clean-break semantic core and Codex/Pi integrations. This document authorizes no migration, production change, installation, or release.

## 1. Executive summary

KAPISCH 3 uses a Python 3.11, stdlib-only **semantic protocol kernel**, canonical Markdown workflow/role contracts, and a versioned, generated JSON **CoreBundle**. The kernel owns semantic types, transition and artifact validation, canonical serialization, and bundle compilation; it knows neither Codex nor Pi. Codex and Pi compile host-native assets from the same bundle in their own build steps and bind their own runtime profiles and capability claims. The LLM/controller still interprets English, inspects repository evidence, and makes scoped judgments; deterministic code checks declared state and evidence but does not pretend to classify prose or certify a review. Fresh v3 JSON authority and Markdown evidence replace v1–v4 TOML state; observational JSONL telemetry is separate and never authoritative. No automatic v2 state migration.

**Intent and constraints:** achieve genuinely portable semantics and cheaper future adapters without losing explicit human gates, reviewer independence, revision-bound evidence, sequential single-writer execution, cold restart, or truthful unavailable information. No v3 production implementation occurs in this design session. Current host behavior is evidence, not a mandate to preserve its mechanisms.

## 5. Goals

The twelve primary goals in the request are acceptance requirements. Specifically a future fake harness must compile and execute the semantic conformance suite without core edits, while Codex/Pi never read each other's artifacts. Behavior, not identical native files or model names, is equivalent across hosts. v3 must be measurably smaller in compatibility/install surface without weakening independent review, human authority or recovery.

## 6. Non-goals

No v2 runtime-state migration, backwards-compatible TOML reader, universal workflow engine, deterministic English intent/risk classifier, model/provider portability guarantee, generic third-party hook framework, automatic capability installation/authentication, external-effect exactly-once claim, or telemetry-driven routing. A standalone review remains findings-only. Implementation, asset regeneration and cutover are explicitly out of this session.

## 7. Architectural principles

1. Core owns semantic role/workflow/gate/authority policy; adapters own host invocation, files, sandbox and packaging.
2. A host asset is a disposable projection, never a semantic source. No cross-harness reads.
3. Human/controller judgment is recorded and checked against explicit constraints; a validator cannot attest to an unobserved fact.
4. Runtime model/provider/profile does not define logical role, tier, risk, or authority.
5. Durable protocol types precede serialization choices. Persist only evidence needed to resume or substantiate a gate.
6. Reject unknown/missing required authority; accept only factual runtime provenance. Cache and telemetry never confer authority.
7. Backward compatibility is opt-in and omitted from 3.0. Safe refusal is not a migration.
8. Expose narrow typed capability/telemetry boundaries, not arbitrary mutating lifecycle hooks.
9. Every consumed durable artifact has a named earlier producer; each generated authority field one owning producer. Cold restart needs validated persisted authority alone, not conversation or caller-supplied claims.

**Choose A**, not from language affinity: one validated implementation of durable invariants already exists in Python, Codex already ships Python CLI, and Pi can consume a prebuilt neutral bundle without parsing Codex TOML or requiring Python during asset generation. Python 3.11 is the **only shipped conformant validator in 3.0** and is required whenever v3 persists or claims authoritative approval, readiness, resumable execution authority, or other validated gate state—even in a graph-free task or accepted advisory path. Findings-only standalone review and non-authoritative advisory research/proposals may run without it. The CoreBundle/protocol defines conformance independently of Python so a later validator can be implemented in another language; no such alternative ships in 3.0. Missing validation blocks the authority claim, never silently waives it.

## 9. Chosen architecture and core domain model

A stdlib Python `kapisch_core` package contains enums/immutable records for `Role`, `Workflow` (`advisory`, `review`, `task`, `milestone`), `Stage` (research, design, implement, review, final, gate, bounded delegate), `Gate` (human decision, approval, side-effect), `AuthorityGrant` (actor/source, exact target/scope/effect, revision/digest, timestamp), `Risk` (low/medium/high), `ExecutionClass` (mechanical/prescriptive/bounded/design), `LogicalTier` (cheap/standard/high), `ReviewDepth` (quick/standard/deep), `ReviewScope` (standalone/iteration/whole-branch), `CapabilityEffect` (repository-read/write, external-read/write, destructive), `Transition`, `EvidenceRef`, and durable run/stage/attempt records. No file extension, `.codex`, `.pi`, provider model, or host path is a domain enum. Domain owns allowed transitions, active-writer count, authority/evidence prerequisites, role admissibility, tier floors, risk-not-reduced rules, and review/final gating.

Workflow boundaries: advisory is graph-free research/design with optional human acceptance and distinct approved promotion plan; review is graph-free findings-only; task is graph-free execution but persists review invocation/result when approval is required; milestone is approved-plan-backed durable sequential execution. Graph-free does not mean validation-free: once an advisory decision or task review becomes authoritative, its gate state requires the conformant validator. No graph is invented solely for a task's review. A material expansion needs new explicit authority. A human approval record is never generated from a model's recommendation. Unsupported effect class blocks. Review/final reports are distinct invocations; bounded iteration reviews may reuse an independent read-only reviewer thread but bind new revision-scoped results; whole-branch review and final use fresh reviewer context. An ordinary one-step task review may cover its entire task diff without duplicate identical reviews. Final requires current whole-branch review and no unreviewed implementation delta. Risk increases depth, not automatic final-readiness requirement. Persistence/state machine must handle failed, interrupted, blocking and terminal transitions rather than treating every report as completion.

## 10. LLM/controller judgment boundary

Controller interprets natural language and explicit controls, chooses workflow/scope/risk/execution class, discovers governing decisions, evaluates actual Git diff and reviewer findings, selects narrow context, and asks humans for meaningful decisions. Core validates declared choices and their evidence against invariants (e.g., high-risk prescriptive cannot dispatch lite; final cannot cite an iteration review; unknown reviewer provenance cannot prove approval). Human approval requires exactly one of: (A) a persisted host-observed inbound human-action receipt, or (B) a human-authored approval artifact. A host/session-local unique action ID suffices; a globally stable provider message ID is **not** required. The host/adapter boundary produces a receipt that itself binds exact inbound action/text digest, run ID, gate/decision ID, exact target/scope or its digest, observed timestamp, and factual inbound-human origin; controller-owned envelope fields cannot retarget a receipt. The controller may persist and reference that host observation, never manufacture it. `Gate.HUMAN_DECISION` records explicit human choice, `Gate.APPROVAL` remains independent reviewer approval, and `Gate.SIDE_EFFECT` records separate permission for an authorized effect. Explicit human approval of a plan is a separate `Gate.HUMAN_DECISION`, not an implication of reviewer approval. For (B), bind the human-authored bytes, run/gate/target and digest without treating controller-written text as human-authored. If neither evidence path is available, authoritative gate completion blocks. Core does **not** parse English, determine whether a finding is genuinely causal, verify human identity cryptographically, infer a model from a filename, or pronounce branch ready from validator exit 0. Fresh independent reviewer judges source and evidence; controller records outcome and checks gate; user retains explicit side-effect approval.

## 11. Canonical prose contracts and CoreBundle

Handwritten sources: one full normative `contracts/roles/<role>.md` for each of six roles; shared workflow/policy Markdown for normalization, risk, dispatch, review, authority, handoff and resume. Remove duplicated role prompt text from adapters. Keep prose for qualitative judgments (scope, causality, adequate evidence, architecture choices); use typed metadata only for closed vocabularies and machine-checkable declarations. Workflow metadata uses `metadata_scope=workflow-specific`: its stages, gates, and review scopes describe workflow-specific requirements, not the full admissible set, a required sequence, or lifecycle transitions. `evaluate_action_policy()` remains the sole static-admissibility authority, and consistency tests validate each declaration against it. The review policy owns Behavioral branch and Invariant evidence matrix applicability/fields/status; the handoff policy owns the complete human decision packet. The concrete lifecycle matrix remains deferred to Stage 7.0. Every contract has stable role/workflow ID and an explicit normatively owned section; projections must include its exact semantic text or a bundle-supplied canonical text assembly, never adapter-maintained paraphrases.

`CoreBundle` is a **generated, versioned canonical JSON resource**, compiled deterministically at build/release time from core typed metadata, canonical Markdown, and v3 JSON Schemas. Includes `protocol_version`, role IDs/contract text and SHA-256, workflow-specific stage/gate/review-scope metadata, artifact schemas, and canonical controller instructions. The bundle digest is SHA-256 of the **entire exact canonical UTF-8 JSON bytes** (sorted keys, LF, no timestamps or paths); to avoid a self-referential hash it lives in the run state, adapter/release manifests and bundle filename, not inside the hashed payload. Python in-memory objects are compilation detail; adapters consume packaged JSON and verify version/digest before projection. At authoritative run creation, validate the distributed bundle, then atomically store or reuse its exact immutable bytes at `.kapisch/v3/bundles/<sha256>.json`; record that digest in run state. Keep bundles referenced by any run locally recoverable across adapter/core upgrades. Resume and every authoritative transition load **that exact stored bundle**, verify its canonical bytes and digest, and block if missing, corrupt or changed; never substitute a different same-protocol bundle. No adapter needs another adapter's source tree, and Pi install need not parse TOML or invoke Python merely to obtain agent definitions. Release embeds the same bundle in each adapter, checked by CI. The CoreBundle and conformance rules are language-neutral public protocol surfaces, not a promise of a Python-only validator API.

## 12. Harness adapter API

Private 3.0 implementation interface, stable enough for a fake harness conformance test but **not** a public SDK:

```text
HarnessCapabilities: named guarantees -> enforced | advisory | unsupported | unknown
RuntimeProfile: preset ID, role/tier -> host model/provider/reasoning settings
GeneratedAsset: relative host path, canonical bytes, source bundle digest
AdapterManifest: adapter version, protocol range, bundle digest, asset digests, capability claims
HarnessAdapter.compile(bundle, profile) -> (assets, manifest)
HarnessAdapter.observe_invocation(...) -> factual provenance or unavailable
HarnessAdapter.observe_human_action(...) -> host-observed inbound-human receipt or unavailable
HarnessAdapter.dispatch(packet) -> observed receipt/result or explicit blocked
HarnessAdapter.reconcile(operation_id) -> observed outcome or unavailable (optional; never retries)
```

Compiler side effects are limited to staged output files in adapter build; runtime dispatch only occurs after validated core state grants it. Dispatch packets carry the persisted unique operation ID. An optional adapter reconciliation operation may read the outcome for that ID but cannot create a second invocation; if the host lacks reliable reconciliation, the run stays blocked. No `before_transition`/arbitrary callback. Controller talks to an adapter boundary, not to generated file semantics; records validated selected role, adapter identity/capability claims and observed invocation IDs, not a host agent filename as proof. Runtime failures/absent capabilities block or take only an explicitly allowed non-degrading fallback.

## 13. Harness capability model

For each capability record `enforced` (host-backed and verified), `advisory` (instruction/allowlist alone), `unsupported`, or `unknown` (not measured); include evidence source and version where available. Describe fresh-context creation, independent reviewer identity/dispatch, filesystem write denial, shell write denial, **host-observed human-action receipt**, nested delegation, runtime metrics, model override, sandbox guarantee and read-only repository evidence access. `unknown` is not `enforced`. Any Pi review claiming authoritative `approve` or `ready` requires an **enforced mutation-free reviewer path**: proven safe read-only repository/Git inspection without mutating shell access, a host-backed read-only sandbox, or equivalent enforced mechanism. Current Pi reviewer/researcher `bash` is advisory about shell-side mutation and insufficient alone. Until an enforcement path is proven, Pi may return findings-only but must block authoritative approve/ready; no fallback may downgrade this gate to preserve v2 behavior. Missing reviewer identity/context also blocks approval. Missing runtime metrics never block workflow and never turn into zero. Adapter conformance must verify any claim it uses as a gate; otherwise downgrade/mark unknown, not trust self-description. Advisory constraints remain meaningful safety instructions but do not masquerade as enforcement.

## 14. Runtime profiles

`balanced`, `quality`, `budget` are adapter-owned distribution presets, not core roles or shared policy. Core has logical tiers and minimum assignment/review guarantees; adapters map each role/tier to available host model/provider/reasoning/sandbox separately and validate that an override does not alter role authority or required capability. No Codex model IDs in CoreBundle. Record requested and observed runtime profile/model separately; unexposed observed values are unavailable. Pre-generate preset assets during release, choose one explicitly at install/activation, and never rewrite the installed template to switch providers. Profile absence cannot degrade reviewer/final gate; explicit selection/blocked status is required.

## 15. Generated assets and ownership

Core authors semantic contracts and metadata exactly once. Codex adapter produces Codex agent TOML, host skill, preset profiles, metadata; Pi adapter produces Pi agent Markdown, Pi skill and package metadata as appropriate. Host policy/sandbox/tool mapping remains handwritten **adapter-local** but cannot redefine role text or gate policy. Build outputs include provenance to bundle digest; CI byte-compares regeneration and refuses manual drift. Plugin/package manifests may be generated when fields derive from release manifest; marketplace install policy remains host-owned. No runtime consumes another host's generated representation.

## 16. Persistence / artifact protocol

Version-3 authority is a new namespace (`.kapisch/v3/runs/<run_id>/`) with strict `protocol_version: 3` and run-pinned `bundle_digest` in its authoritative state. The exact immutable CoreBundle bytes live outside runs at `.kapisch/v3/bundles/<sha256>.json`; every authoritative run verifies and stores/reuses its bundle before creating gate state, and retains it while the run can resume. Bundle bytes are canonical JSON whose whole-byte SHA-256 equals the directory key. A findings-only standalone review or non-authoritative advisory research/proposal need not create authority state or invoke a validator. v2 `.kapisch/runs/*`, TOML and legacy `.planning/*` are detected and refused for resume; no silent conversion or dual-reader path. Canonical JSON is used for run state/graph, stage attempts/outcomes with a `stage_kind` distinct from stable `stage_id`, approval/decision and invocation/delegation records. Markdown holds human proposals, scope/plan and reports; bytes of evidence actually cited are digest-bound. Optional JSONL is **telemetry/benchmark only**, not a replay log or authority. No TOML protocol.

Each accepted advisory snapshot is a **separate immutable canonical JSON artifact** produced at human acceptance. It binds every discovered active governing decision and direct authority source by kind, path, byte digest, and applicable decision/snapshot ID, and contains explicit `amends`/`supersedes` edges to immutable earlier snapshots. Dependency entries may include optional `decision_id` and `snapshot_id`, individually or together. `kind=decision` requires `decision_id`, `kind=snapshot` requires `snapshot_id`, and direct-source kinds may omit both. When a decision is bound through its containing snapshot, both IDs identify that relationship; every supplied ID must resolve to the referenced artifact. Mutable run state contains only the accepted snapshot's ID, path and digest plus `amends`/`supersedes` arrays of snapshot IDs; both arrays are required when an accepted snapshot exists and must match its immutable edges. These references are checked against snapshot bytes; state never embeds or rewrites accepted snapshot content. Snapshot filenames use stable IDs, not mandatory content-addressing. Human acceptance cannot silently override a still-active normative source. Proposal-ready, acceptance, plan approval, promotion, execution start, and resume recheck applicability, relationships, and current dependency bytes; unresolved conflict blocks. A changed governing file makes the *plan/execution* stale until an explicit re-evaluation and fresh approval, not the historical accepted snapshot invalid. Completeness of authority discovery remains controller/architect judgment; structural validation checks every declared binding and conflicts it can observe.

Producer chain: controller creates scope/intent and run state; researcher/architect/reviewer/delegate return bounded reports, but **controller** persists their exact bytes and binds returned evidence; human supplies explicit decisions through a host/adapter-produced inbound-human receipt (or independently human-authored artifact), controller persists its exact source/scope and may not manufacture either kind of human evidence; controller produces the separate immutable accepted snapshot at acceptance, then records only its ID/path/digest and relationship references in mutable state; controller approves a plan only after human approval and binds immutable source bytes; controller records assignment and prepares a planned invocation, then atomically persists `dispatch-uncertain` **before** adapter dispatch; adapter supplies factual invocation receipt; controller persists terminal result/verification; validator consumes only records whose references, content, revisions and producer sequence validate; controller derives next action; renderer alone produces replaceable controller view. Generated authority fields have one owner: controller for decisions/state/references and accepted-snapshot serialization, host/adapter for human-action provenance, adapter for attested invocation fields, reviewer for review judgment content, human for approval input/artifact. Controller transports rather than invents externally owned facts. No derived view/telemetry is a producer of authority.

Persist one bounded authoritative run-state JSON with ordered immutable attempt/gate records and reference paths; publish each immutable report/outcome first, then atomically replace the state snapshot pointing to it. Before **any** adapter dispatch call, atomically persist a stable invocation ID, exact request and `dispatch-uncertain` (in-flight) status. A crash after this point—even if no call was sent—blocks redispatch unless the provider can reliably reconcile that exact operation ID without repeating its effect; do not treat a missing receipt as proof of no dispatch. Persist the adapter's factual receipt and terminal result separately when observed. A crash after evidence before state yields an orphan ignored until explicit reconciliation. No separate authoritative recovery journal or event replay engine in 3.0. Single active writer per run and atomic same-filesystem publication with process lock where needed; after cold restart validator checks path containment, closed fields, cross-record references, monotonic stage history, revision/scope/authority/digest bindings, then reconciles Git and provider observations. No caller claim or unpersisted session state may supply missing authority. Hash immutable approved decisions/plans, invoked review packets/results, delegated context/result, stage verification and final source binding; hash semantic bundle and generated assets. Do **not** content-address telemetry, routine mutable state or all prose merely for uniformity. Canonical JSON excludes clocks and environment-dependent fields from reproducible derived payloads; observed timestamps remain factual, not deterministic. Hashes detect accidental/stale binding, not forgery by a privileged writer.

Review/final invocation authority includes exact target/base/head plus a canonical **RepositoryStateFingerprint** at pre-dispatch, post-result and current validation/resume. This host-neutral semantic structure contains the repository object-ID algorithm and HEAD commit identity; canonical index/staged entries (repository-relative path, stage, object ID and mode, including unmerged stages); canonical tracked working-tree facts (path, type/mode, content digest or deletion); and canonical untracked path inventory with exact byte digests for explicitly included untracked evidence. Derive these facts from Git objects and file content, not raw `.git/index` bytes, stat caches, timestamps, configured diff rendering, color, textconv, or external diff output. Stable repository-relative path encoding, ordering and serialization are protocol-defined and deterministic across hosts. Relevant untracked files must be absent for approval unless explicitly included with byte-bound evidence under the declared review scope; changes to their paths or included bytes stale approval. Approval requires equivalent pre/post fingerprints; resume and final-readiness checks independently recompute the current fingerprint and reject material state changes even when HEAD is unchanged. Reviewer-returned target/fingerprint must match the persisted invocation. Store these fingerprints in authoritative review evidence, never only telemetry. Command-level Git extraction belongs in the implementation plan, not this semantic definition.

## 17. Validation

The shipped Python 3.11 v3 validator is required for **any** workflow that persists or claims authoritative approval, readiness, resumable execution authority, or other validated gate state, including graph-free task review and accepted advisory decisions/plans. Findings-only standalone review and non-authoritative advisory work do not require it. One v3-only validator validates schema/closed vocabularies, strict path/revision/digest and producer binding, exact locally retained CoreBundle bytes, governing-authority dependency freshness, complete pre/post/current `RepositoryStateFingerprint`, admissible transitions, one active writer, complete attempt/gate provenance, human evidence provenance and target binding, plan/promotion approval, reviewer invocation state and separate final, unsupported delegated effects and v2 refusal. Structural exit 0 is necessary, never sufficient for independence, causality, human intent or actual readiness. The validator must obtain current repository facts through a host-neutral repository-inspection boundary and independently derive the current fingerprint; a controller-supplied current fingerprint alone is not evidence of freshness. Validate previous persisted snapshot when available, but cold-restart correctness cannot depend on it; current run must contain enough append-only history and evidence to establish its state. An unknown/newer version fails closed without rewriting. Keep tested deterministic serialization and typed errors; delete v1–v4 parsing branches rather than copying them. Conformance is defined by versioned protocol inputs, outputs and acceptance scenarios, not by Python imports or callable signatures, so a later independently implemented validator can satisfy the same contract.

## 18. Installation and lifecycle

Core wheel/resource/CLI is independently installable; adapter distributions embed/identify the compatible bundle and validate it before use. Codex installer selects prebuilt `balanced|quality|budget` assets at project/user scope with collision detection, no silent overwrite, explicit managed ownership, drift check and uninstall that touches only verified owned files. Pi local package ships self-contained skill/agents and declares `pi-subagents` integration; installation never reads Codex plugin files. No automatic auth, model provisioning, profile switch transaction, or consumer-side TOML rewrite. If atomic multi-file install is required for safety, stage then publish or reject partial state; retain no v2 journal protocol. Version resolution checks protocol compatibility for new runs; existing runs additionally require their exact retained bundle bytes, not merely a compatible version.

## 19. Extension/plugin model

Private typed `CapabilityProvider` can expose a named bounded effect with required authority and idempotency/reconciliation properties; cannot select workflow, mutate gates or pretend to be reviewer. Private `TelemetrySink` receives immutable best-effort observation events and cannot return policy decisions. **Public/stable 3.0 surfaces are only** the documented CoreBundle format, protocol compatibility rules, documented telemetry schema and adapter conformance expectations. Python adapter classes, provider/sink interfaces and internal registration/discovery remain private implementation APIs with no third-party compatibility promise in 3.0. No public Python plugin API or generic lifecycle hooks. External write/destructive provider remains unsupported until pre-intent, provider operation identity, read-only reconciliation and interruption tests prove safe blocking; approval alone does not imply retry safety.

## 20. Telemetry protocol

Optional append-only UTF-8 JSONL sidecar, schema `kapisch.telemetry/1`, separate from `.kapisch/v3/runs` authority (e.g. ignored `.kapisch/telemetry/<run_id>.jsonl`). The documented telemetry schema is a public 3.0 surface; the sink implementation/API is not. Envelope: `schema`, `event_id`, observed UTC `timestamp`, `run_id`, `harness`, nullable `session_id`/`parent_session_id`/`agent_run_id`, `workflow`, nullable `stage_id`/`role`, `status`, and `extensions` keyed by reverse-domain harness namespace. Event types: `run.started`, `workflow.selected`, `stage.started`, `agent.dispatched`, `agent.completed`, `gate.requested`, `gate.resolved`, `review.completed`, `retry.started`, `delegation.started`, `delegation.completed`, `run.completed`. Event-specific fields include factual review decision/finding count and optional elapsed milliseconds, input/output/cache-read tokens, turn count, requested/observed model/runtime metadata; **each unavailable measurement is JSON null with no inference** (including missing session lineage). Schema validates observed field shape, not authority. Best-effort sink failure cannot advance/block a gate or change routing; no validator reads telemetry; telemetry cannot replace invocation/result artifacts or Git evidence. `pi-session-inspector` may later consume this public observational JSONL, but core imports nothing from it. Existing `docs/controller-benchmark.md` JSONL metrics and null convention can be mapped conceptually, not adopted as workflow state. Never infer provider tokens from text length or infer model from configured defaults.

## 23. Testing strategy

- **Core:** typed policy floors, permitted transitions, human/side-effect gates, advisory promotion and governing-dependency staleness/supersession, immutable separate snapshot and mutable pointer checks, findings-only review/advisory with no validator, graph-free task review/advisory acceptance blocked without a conformant validator, exact human-receipt or human-authored approval-artifact provenance/target binding (including a host-local ID without provider-global ID), deterministic bytes/digests, retained exact bundle after adapter upgrade, missing/corrupt/same-version-different bundle refusal, v2 refusal, cold restart from current authority alone, unknown/malformed evidence refusal, one-writer resume, and crash tests immediately before/after adapter call and receipt publication proving uncertain dispatch never repeats. Change HEAD, staged index object/mode, tracked worktree content/mode, untracked inventory and explicitly included untracked bytes separately; each material change must stale approving review/final evidence. Equivalent Git/content facts under changed index stat cache, timestamp or diff configuration must keep the same fingerprint.
- **Adapter conformance:** compile six roles from identical bundle, no semantic rewrites, declared capability verification, unknown/advisory downgrades, no cross-host read, missing reviewer, unsupported effect, fake harness without core modification; Pi `bash` alone must fail enforced reviewer capability, while a proven mutation-free reviewer path may support authoritative review. Verify host/adapter receipt ownership independently of controller-supplied fields.
- **Goldens:** byte-stable bundled contract/JSON schemas and Codex TOML/Pi Markdown for each preset, provenance digests; golden changes reviewed as semantic or adapter-specific diffs.
- **Integration:** Codex invocation/sandbox/profile/marketplace collision and drift; Pi package/subagent mapping, missing conformant validator on graph-free authoritative and durable paths, shell read-only limitation and findings-only fallback; no assumption of identical host sandbox.
- **Platform:** Windows path/atomic-install checks only for platform-sensitive Codex tooling; cross-platform canonical JSON smoke as needed, not full unrelated core acceptance rerun.
- **Semantic acceptance:** split scenarios by semantic responsibility using shared focused builders/fixtures; do not require one monolithic acceptance module. Cover same scenario in fake/Codex/Pi with host-specific transport: standalone review; bounded behavioral task + independent review; approved durable milestone; blocking review→fix→new review; final whole-branch readiness; cold resume and ambiguous result; missing reviewer; insufficient host enforcement; high risk never cheap/deep review preserved; prohibited delegated external effect. Compare decisions and evidence prerequisites, not raw agent-file bytes.
- **Release:** one bundle/protocol compatibility matrix, reproducible projections, package contents, two host smoke tests and v2 detection/refusal. Retire legacy compatibility fixtures when cutover completes.

## 24. Migration and cutover strategy

1. Freeze v2 behavior on a maintained release branch/tags (do not mutate v2 runtime state); accept design and record decisions.
2. Introduce v3 core types/contracts and JSON bundle **without** changing current runtime authority; prove bundle contains no host fields and a fake adapter can consume it.
3. Introduce fresh v3 artifacts/validator in new namespace; prove cold-restart and producer-ownership invariants. Never allow a v2 and v3 artifact to govern the same run.
4. Build adapter conformance first, then Codex and Pi projections independently in staged packages. Only one selected adapter projection is active for a consumer installation; legacy plugin remains v2-only until deliberate 3.0 activation.
5. Add best-effort telemetry after authority tests, not before.
6. Cut release branch to v3 only when both adapters pass common scenarios; remove legacy readers/installers from v3 tree, preserve v2 branch/tags, refuse old run state; no automatic migration.
7. Publish only on explicit later release authorization. A broken staged adapter rolls back to unchanged v2 package or a new v3 build; no mixed-authority fallback.

## 27. Hard architectural invariants

1. `core/` imports no host/tooling module, mentions no `.codex`/`.pi` path, provider ID, TOML field or marketplace convention in executable domain/schema/bundle.
2. Neither adapter reads another adapter's generated files; every host-native agent file comes from verified CoreBundle + local runtime policy.
3. Exactly one handwritten semantic source for each role; generated files fail CI when stale.
4. Logical tier contains no model/provider; profile changes do not alter role authority, risk, review scope or gates.
5. Validator rejects missing/unknown human authority (including incomplete host/session-local inbound-human receipt or missing human-authored approval artifact), reviewer invocation/result, revision or producer bindings; any authoritative gate, graph-free or durable, requires a conformant validator. Python 3.11 is the sole shipped 3.0 implementation, not a language restriction on the protocol.
6. Review/final have distinct current invocations; standalone findings cannot approve; Pi's unproven shell-side read-only policy cannot approve/declare ready; later implementation invalidates prior final readiness.
7. Each durable consumer has an earlier explicit producer and each authority field has one owning producer; cold restart is reconstructible from persisted validated authority, exact retained immutable bundle bytes under their digest and current repository/provider evidence, not memory/caller assertion.
8. One active durable writer; an in-flight dispatch marker is persisted before the adapter call; uncertain external or dispatched effect blocks rather than repeats; completed verified work is not redispatched.
9. Review/final authority binds pre/post/current semantic `RepositoryStateFingerprint`, not raw index bytes, rendered diffs or HEAD alone; governing dependencies are checked at promotion/start/resume without rewriting separately stored immutable accepted snapshots.
10. Telemetry and controller view are non-authoritative; null measurements stay null and never affect routing.
11. v2 state detected/refused; fake harness passes shared contract unchanged; Windows-only behavior stays in relevant adapter tests.
12. The documented bundle, protocol compatibility, telemetry schema and conformance expectations are public; adapter/provider/sink classes and discovery remain private in 3.0.

## 28. Risks and trade-offs

Python 3.11 remains the only shipped 3.0 validator runtime for authority-bearing gates, including graph-free authoritative approval; a future independently implemented conformant validator is allowed by the protocol. Pi cannot produce authoritative approve/ready until an enforced mutation-free reviewer path is proven; findings-only remains available. Exact bundle retention prevents ordinary upgrades from silently changing run semantics but requires protecting referenced bundle files. A neutral JSON bundle is a boundary, not a claim that Markdown can be compiled into fully enforceable semantics; conformance tests must catch projection omissions. A single run-state file simplifies restart but requires bounded history and atomic publication; enforce size limits and monitor before considering an authoritative append-only journal. Cross-file crash windows yield safe orphan cleanup/reconciliation rather than automatic completion. Digests bind bytes but do not prove human authorship or defend against a malicious privileged controller. Semantic repository fingerprinting needs cross-platform canonical Git/content rules, not display-level diff capture. Removing state migration is disruptive but intentional; keep v2 readers available through v2 distribution.

## 29. Closed decisions and remaining open questions

1. **Validator:** Python 3.11 is the sole shipped conformant validator in 3.0. Every authority-bearing gate, including graph-free authoritative approval/readiness, needs validation; findings-only standalone review and non-authoritative advisory work do not. Future language-independent conformant implementations remain possible under the public protocol.
2. **Pi reviewer enforcement:** authoritative `approve`/`ready` requires a proven enforced mutation-free inspection path; current Pi `bash` permission policy alone does not qualify. Until then Pi returns findings only and blocks those decisions.
3. **API exposure:** CoreBundle format, protocol compatibility rules, documented telemetry schema and adapter conformance expectations are public. Python adapter classes, `CapabilityProvider`, `TelemetrySink`, registration and discovery are private in 3.0.
4. **Snapshots:** every accepted advisory snapshot is a separate immutable canonical JSON artifact. Mutable state stores ID/path/digest and verified amendment/supersession references, not snapshot content; no content-addressed filename requirement.
5. **Human gate evidence:** either host/adapter-produced inbound-human action receipt with session-local ID and exact provenance/target binding, or an independently human-authored approval artifact. No globally stable provider ID requirement; controller never fabricates either source.
6. **Bundle retention:** run creation stores exact bundle bytes at `.kapisch/v3/bundles/<sha256>.json`; resume verifies and loads that bundle rather than the upgraded distribution copy.
7. **Repository state:** canonical `RepositoryStateFingerprint` uses stable Git/content facts for pre/post/current checks, not raw index serialization or rendered diffs.

**Remaining architecture questions:** none introduced by these amendments. Implementation details such as exact Git extraction commands and host capability proofs are acceptance work for the implementation plan, not authority to weaken these decisions. This specification is accepted as the normative KAPISCH v3 architecture contract.
