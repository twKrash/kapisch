# KAPISCH 3.0 architecture design

Date: 2026-09-29
Status: **accepted architecture contract** (explicit user approval); implementation governed by the separately accepted plan.
Scope: clean-break semantic core and Codex/Pi integrations. This document authorizes no migration, production change, installation, or release.

## 1. Executive summary

KAPISCH 3 uses a Python 3.11, stdlib-only **semantic protocol kernel**, canonical Markdown workflow/role contracts, and a versioned, generated JSON **CoreBundle**. The kernel owns semantic types, transition and artifact validation, canonical serialization, and bundle compilation; it knows neither Codex nor Pi. Codex and Pi compile host-native assets from the same bundle in their own build steps and bind their own runtime profiles and capability claims. The LLM/controller still interprets English, inspects repository evidence, and makes scoped judgments; deterministic code checks declared state and evidence but does not pretend to classify prose or certify a review. Fresh v3 JSON authority and Markdown evidence replace v1–v4 TOML state; observational JSONL telemetry is separate and never authoritative. No automatic v2 state migration.

**Intent and constraints:** achieve genuinely portable semantics and cheaper future adapters without losing explicit human gates, reviewer independence, revision-bound evidence, sequential single-writer execution, cold restart, or truthful unavailable information. No v3 production implementation occurs in this design session. Current host behavior is evidence, not a mandate to preserve its mechanisms.

## 5. Goals

The twelve primary goals in the request are acceptance requirements. Specifically a future fake harness must compile and execute the semantic conformance suite without core edits, while Codex/Pi never read each other's artifacts. Behavior, not identical native files or model names, is equivalent across hosts. v3 must be measurably smaller in compatibility/install surface without weakening independent review, human authority or recovery.

## 6. Non-goals

No v2 runtime-state migration, backwards-compatible TOML reader, universal workflow engine, deterministic English intent/risk classifier, model/provider portability guarantee, generic third-party hook framework, automatic capability installation/authentication, external-effect exactly-once claim, or telemetry-driven routing. A standalone review remains findings-only. Implementation, asset regeneration and cutover are explicitly out of this session.

## 7. Architectural principles

1. Core owns semantic role/workflow/gate/authority policy; adapters own host invocation, files, sandbox and packaging.
2. A host asset is a disposable projection, never a semantic source. No cross-harness reads.
3. Human/controller judgment is recorded and checked against explicit constraints; a validator cannot attest to an unobserved fact.
4. Runtime model/provider/profile does not define logical role, tier, risk, or authority.
5. Durable protocol types precede serialization choices. Persist only evidence needed to resume or substantiate a gate.
6. Reject unknown/missing required authority; accept only factual runtime provenance. Cache and telemetry never confer authority.
7. Backward compatibility is opt-in and omitted from 3.0. Safe refusal is not a migration.
8. Expose narrow typed capability/telemetry boundaries, not arbitrary mutating lifecycle hooks.
9. Every consumed durable artifact has a named earlier producer; each generated authority field one owning producer. Cold restart needs validated persisted authority alone, not conversation or caller-supplied claims.

**Choose A**, not from language affinity: one validated implementation of durable invariants already exists in Python, Codex already ships Python CLI, and Pi can consume a prebuilt neutral bundle without parsing Codex TOML or requiring Python during asset generation. The CoreBundle/protocol defines conformance independently of Python so a later validator can be implemented in another language; no such alternative ships in 3.0. ## 9. Chosen architecture and core domain model

A stdlib Python `kapisch_core` package contains enums/immutable records for `Role`, `Workflow` (`advisory`, `review`, `task`, `milestone`), `Stage` (research, design, implement, review, final, gate, bounded delegate), `Gate` (human decision, approval, side-effect), `AuthorityGrant` (actor/source, exact target/scope/effect, revision/digest, timestamp), `Risk` (low/medium/high), `ExecutionClass` (mechanical/prescriptive/bounded/design), `LogicalTier` (cheap/standard/high), `ReviewDepth` (quick/standard/deep), `ReviewScope` (standalone/iteration/whole-branch), `CapabilityEffect` (repository-read/write, external-read/write, destructive), `Transition`, `EvidenceRef`, and durable run/stage/attempt records. No file extension, `.codex`, `.pi`, provider model, or host path is a domain enum. Domain owns allowed transitions, active-writer count, authority/evidence prerequisites, role admissibility, tier floors, risk-not-reduced rules, and review/final gating.

Workflow boundaries: advisory is graph-free research/design with optional human acceptance and distinct approved promotion plan; review is graph-free findings-only; task is graph-free execution but persists review invocation/result when approval is required; milestone is approved-plan-backed durable sequential execution. Graph-free does not mean validation-free: once an advisory decision or task review becomes authoritative, its gate state requires the conformant validator. Graph-free authoritative work also requires the immutable applicability-scope descriptor defined in §30; it is not an execution graph or milestone node-scope artifact. No graph is invented solely for a task's review. A material expansion needs new explicit authority. A human approval record is never generated from a model's recommendation. Unsupported effect class blocks. Review/final reports are distinct invocations; bounded iteration reviews may reuse an independent read-only reviewer thread but bind new revision-scoped results; whole-branch review and final use fresh reviewer context. An ordinary one-step task review may cover its entire task diff without duplicate identical reviews. Final requires current whole-branch review and no unreviewed implementation delta. Risk increases depth, not automatic final-readiness requirement. Persistence/state machine must handle failed, interrupted, blocking and terminal transitions rather than treating every report as completion.

## 10. LLM/controller judgment boundary

Controller interprets natural language and explicit controls, chooses workflow/scope/risk/execution class, discovers governing decisions, evaluates actual Git diff and reviewer findings, selects narrow context, and asks humans for meaningful decisions. Core validates declared choices and their evidence against invariants (e.g., high-risk prescriptive cannot dispatch lite; final cannot cite an iteration review; unknown reviewer provenance cannot prove approval). Human approval requires exactly one of: (A) a persisted host-observed inbound human-action receipt, or (B) a human-authored approval artifact. A host/session-local unique action ID suffices; a globally stable provider message ID is **not** required. The host/adapter boundary produces a receipt that itself binds exact inbound action/text digest, run ID, gate/decision ID, exact target/scope or its digest, observed timestamp, and factual inbound-human origin; controller-owned envelope fields cannot retarget a receipt. The controller may persist and reference that host observation, never manufacture it. `Gate.HUMAN_DECISION` records explicit human choice, `Gate.APPROVAL` remains independent reviewer approval, and `Gate.SIDE_EFFECT` records separate permission for an authorized effect. Explicit human approval of a plan is a separate `Gate.HUMAN_DECISION`, not an implication of reviewer approval. For (B), bind the human-authored bytes, run/gate/target and digest without treating controller-written text as human-authored. If neither evidence path is available, authoritative gate completion blocks. Core does **not** parse English, determine whether a finding is genuinely causal, verify human identity cryptographically, infer a model from a filename, or pronounce branch ready from validator exit 0. Fresh independent reviewer judges source and evidence; controller records outcome and checks gate; user retains explicit side-effect approval.

## 11. Canonical prose contracts and CoreBundle

Handwritten sources: one full normative `contracts/roles/<role>.md` for each of six roles; shared workflow/policy Markdown for normalization, risk, dispatch, review, authority, handoff and resume. Remove duplicated role prompt text from adapters. Keep prose for qualitative judgments (scope, causality, adequate evidence, architecture choices); use typed metadata only for closed vocabularies and machine-checkable declarations. Workflow metadata uses `metadata_scope=workflow-specific`: its stages, gates, and review scopes describe workflow-specific requirements, not the full admissible set, a required sequence, or lifecycle transitions. `evaluate_action_policy()` remains the sole static-admissibility authority, and consistency tests validate each declaration against it. The review policy owns Behavioral branch and Invariant evidence matrix applicability/fields/status; the handoff policy owns the complete human decision packet. The concrete lifecycle matrix remains deferred to Stage 7.0. Every contract has stable role/workflow ID and an explicit normatively owned section; projections must include its exact semantic text or a bundle-supplied canonical text assembly, never adapter-maintained paraphrases.

`CoreBundle` is a **generated, versioned canonical JSON resource**, compiled deterministically at build/release time from core typed metadata, canonical Markdown, and v3 JSON Schemas. Includes `protocol_version`, role IDs/contract text and SHA-256, workflow-specific stage/gate/review-scope metadata, artifact schemas, and canonical controller instructions. The bundle digest is SHA-256 of the **entire exact canonical UTF-8 JSON bytes** (sorted keys, LF, no timestamps or paths); to avoid a self-referential hash it lives in the run state, adapter/release manifests and bundle filename, not inside the hashed payload. Python in-memory objects are compilation detail; adapters consume packaged JSON and verify version/digest before projection. At authoritative run creation, validate the distributed bundle, then atomically store or reuse its exact immutable bytes at `.kapisch/v3/bundles/<sha256>.json`; record that digest in run state. Keep bundles referenced by any run locally recoverable across adapter/core upgrades. Resume and every authoritative transition load **that exact stored bundle**, verify its canonical bytes and digest, and block if missing, corrupt or changed; never substitute a different same-protocol bundle. No adapter needs another adapter's source tree, and Pi install need not parse TOML or invoke Python merely to obtain agent definitions. Release embeds the same bundle in each adapter, checked by CI. The CoreBundle and conformance rules are language-neutral public protocol surfaces, not a promise of a Python-only validator API.

## 12. Harness adapter API

Private 3.0 implementation interface, stable enough for a fake harness conformance test but **not** a public SDK:

```text
HarnessCapabilities: named guarantees -> enforced | advisory | unsupported | unknown
RuntimeProfile: preset ID, role/tier -> host model/provider/reasoning settings
GeneratedAsset: relative host path, canonical bytes, source bundle digest
AdapterManifest: adapter version, protocol range, bundle digest, asset digests, capability claims
HarnessAdapter.compile(bundle, profile) -> (assets, manifest)
HarnessAdapter.observe_invocation(...) -> factual provenance or unavailable
HarnessAdapter.observe_human_action(...) -> host-observed inbound-human receipt or unavailable
HarnessAdapter.dispatch(packet) -> observed receipt/result or explicit blocked
HarnessAdapter.reconcile(operation_id) -> observed outcome or unavailable (optional; never retries)
```

Compiler side effects are limited to staged output files in adapter build; runtime dispatch only occurs after validated core state grants it. Dispatch packets carry the persisted unique operation ID. An optional adapter reconciliation operation may read the outcome for that ID but cannot create a second invocation; if the host lacks reliable reconciliation, the run stays blocked. No `before_transition`/arbitrary callback. Controller talks to an adapter boundary, not to generated file semantics; records validated selected role, adapter identity/capability claims and observed invocation IDs, not a host agent filename as proof. Runtime failures/absent capabilities block or take only an explicitly allowed non-degrading fallback.

## 13. Harness capability model

For each capability record `enforced` (host-backed and verified), `advisory` (instruction/allowlist alone), `unsupported`, or `unknown` (not measured); include evidence source and version where available. Describe fresh-context creation, independent reviewer identity/dispatch, filesystem write denial, shell write denial, **host-observed human-action receipt**, nested delegation, runtime metrics, model override, sandbox guarantee and read-only repository evidence access. `unknown` is not `enforced`. Any Pi review claiming authoritative `approve` or `ready` requires an **enforced mutation-free reviewer path**: proven safe read-only repository/Git inspection without mutating shell access, a host-backed read-only sandbox, or equivalent enforced mechanism. Current Pi reviewer/researcher `bash` is advisory about shell-side mutation and insufficient alone. Until an enforcement path is proven, Pi may return findings-only but must block authoritative approve/ready; no fallback may downgrade this gate to preserve v2 behavior. Missing reviewer identity/context also blocks approval. Missing runtime metrics never block workflow and never turn into zero. Adapter conformance must verify any claim it uses as a gate; otherwise downgrade/mark unknown, not trust self-description. Advisory constraints remain meaningful safety instructions but do not masquerade as enforcement.

## 14. Runtime profiles

`balanced`, `quality`, `budget` are adapter-owned distribution presets, not core roles or shared policy. Core has logical tiers and minimum assignment/review guarantees; adapters map each role/tier to available host model/provider/reasoning/sandbox separately and validate that an override does not alter role authority or required capability. No Codex model IDs in CoreBundle. Record requested and observed runtime profile/model separately; unexposed observed values are unavailable. Pre-generate preset assets during release, choose one explicitly at install/activation, and never rewrite the installed template to switch providers. Profile absence cannot degrade reviewer/final gate; explicit selection/blocked status is required.

## 15. Generated assets and ownership

Core authors semantic contracts and metadata exactly once. Codex adapter produces Codex agent TOML, host skill, preset profiles, metadata; Pi adapter produces Pi agent Markdown, Pi skill and package metadata as appropriate. Host policy/sandbox/tool mapping remains handwritten **adapter-local** but cannot redefine role text or gate policy. Build outputs include provenance to bundle digest; CI byte-compares regeneration and refuses manual drift. Plugin/package manifests may be generated when fields derive from release manifest; marketplace install policy remains host-owned. No runtime consumes another host's generated representation.

## 16. Persistence / artifact protocol

Version-3 authority is a new namespace (`.kapisch/v3/runs/<run_id>/`) with strict `protocol_version: 3` and run-pinned `bundle_digest` in its authoritative state. The exact immutable CoreBundle bytes live outside runs at `.kapisch/v3/bundles/<sha256>.json`; every authoritative run verifies and stores/reuses its bundle before creating gate state, and retains it while the run can resume. Bundle bytes are canonical JSON whose whole-byte SHA-256 equals the directory key. A findings-only standalone review or non-authoritative advisory research/proposal need not create authority state or invoke a validator. v2 `.kapisch/runs/*`, TOML and legacy `.planning/*` are detected and refused for resume; no silent conversion or dual-reader path. Canonical JSON is used for run state/graph, stage attempts/outcomes with a `stage_kind` distinct from stable `stage_id`, approval/decision and invocation/delegation records. Markdown holds human proposals, scope/plan and reports; bytes of evidence actually cited are digest-bound. Optional JSONL is **telemetry/benchmark only**, not a replay log or authority. No TOML protocol.

Each accepted advisory snapshot is a **separate immutable canonical JSON artifact** produced at human acceptance. It binds every discovered active governing decision and direct authority source by kind, path, byte digest, and applicable decision/snapshot ID, and contains explicit `amends`/`supersedes` edges to immutable earlier snapshots. Dependency entries may include optional `decision_id` and `snapshot_id`, individually or together. `kind=decision` requires `decision_id`, `kind=snapshot` requires `snapshot_id`, and direct-source kinds may omit both. When a decision is bound through its containing snapshot, both IDs identify that relationship; every supplied ID must resolve to the referenced artifact. Mutable run state contains only the accepted snapshot's ID, path and digest plus `amends`/`supersedes` arrays of snapshot IDs; both arrays are required when an accepted snapshot exists and must match its immutable edges. These references are checked against snapshot bytes; state never embeds or rewrites accepted snapshot content. Snapshot filenames use stable IDs, not mandatory content-addressing. Human acceptance cannot silently override a still-active normative source. Proposal-ready, acceptance, plan approval, promotion, execution start, and resume recheck applicability, relationships, and current dependency bytes; unresolved conflict blocks. A changed governing file makes the _plan/execution_ stale until an explicit re-evaluation and fresh approval, not the historical accepted snapshot invalid. Completeness of authority discovery remains controller/architect judgment; structural validation checks every declared binding and conflicts it can observe.

Producer chain: controller creates scope/intent and run state; researcher/architect/reviewer/delegate return bounded reports, but **controller** persists their exact bytes and binds returned evidence; human supplies explicit decisions through a host/adapter-produced inbound-human receipt (or independently human-authored artifact), controller persists its exact source/scope and may not manufacture either kind of human evidence; controller produces the separate immutable accepted snapshot at acceptance, then records only its ID/path/digest and relationship references in mutable state; controller approves a plan only after human approval and binds immutable source bytes; controller records assignment and prepares a planned invocation, then atomically persists `dispatch-uncertain` **before** adapter dispatch; adapter supplies factual invocation receipt; controller persists terminal result/verification; validator consumes only records whose references, content, revisions and producer sequence validate; controller derives next action; renderer alone produces replaceable controller view. Generated authority fields have one owner: controller for decisions/state/references and accepted-snapshot serialization, host/adapter for human-action provenance, adapter for attested invocation fields, reviewer for review judgment content, human for approval input/artifact. Controller transports rather than invents externally owned facts. No derived view/telemetry is a producer of authority.

Persist one bounded authoritative run-state JSON with ordered immutable attempt/gate records and reference paths; publish each immutable report/outcome first, then atomically replace the state snapshot pointing to it. Before **any** adapter dispatch call, atomically persist a stable invocation ID, exact request and `dispatch-uncertain` (in-flight) status. A crash after this point—even if no call was sent—blocks redispatch unless the provider can reliably reconcile that exact operation ID without repeating its effect; do not treat a missing receipt as proof of no dispatch. Persist the adapter's factual receipt and terminal result separately when observed. A crash after evidence before state yields an orphan ignored until explicit reconciliation. No separate authoritative recovery journal or event replay engine in 3.0. Single active writer per run and atomic same-filesystem publication with process lock where needed; after cold restart validator checks path containment, closed fields, cross-record references, monotonic stage history, revision/scope/authority/digest bindings, then reconciles Git and provider observations. No caller claim or unpersisted session state may supply missing authority. Hash immutable approved decisions/plans, invoked review packets/results, delegated context/result, stage verification and final source binding; hash semantic bundle and generated assets. Do **not** content-address telemetry, routine mutable state or all prose merely for uniformity. Canonical JSON excludes clocks and environment-dependent fields from reproducible derived payloads; observed timestamps remain factual, not deterministic. Hashes detect accidental/stale binding, not forgery by a privileged writer.

Review/final invocation authority includes exact target/base/head plus a canonical **RepositoryStateFingerprint** at pre-dispatch, post-result and current validation/resume. This host-neutral semantic structure contains the repository object-ID algorithm and HEAD commit identity; canonical index/staged entries (repository-relative path, stage, object ID and mode, including unmerged stages); canonical tracked working-tree facts (path, type/mode, content digest or deletion); and canonical untracked path inventory with exact byte digests for explicitly included untracked evidence. Derive these facts from Git objects and file content, not raw `.git/index` bytes, stat caches, timestamps, configured diff rendering, color, textconv, or external diff output. Stable repository-relative path encoding, ordering and serialization are protocol-defined and deterministic across hosts. Relevant untracked files must be absent for approval unless explicitly included with byte-bound evidence under the declared review scope; changes to their paths or included bytes stale approval. Approval requires equivalent pre/post fingerprints; resume and final-readiness checks independently recompute the current fingerprint and reject material state changes even when HEAD is unchanged. Reviewer-returned target/fingerprint must match the persisted invocation. Store these fingerprints in authoritative review evidence, never only telemetry.

For Stage 6 implementation, the repository-state contract is schema-preserving: tracked modes are `100644`, `100755`, `120000`, or deletion `000000`; included untracked evidence accepts regular files only and does not bind executable mode; `--exclude-standard` inventory is deterministic only for equal effective ignore policy; and the tracked universe is the current index-path set. HEAD-only staged deletions, skip-worktree/sparse states, sparse-index states, and gitlinks are represented or rejected exactly as specified by the implementation plan, never guessed or silently omitted. Command-level Git extraction belongs in the implementation plan, not this semantic definition.

### 30.1 Authority domain and applicability

An **authority domain** is the namespace in which immutable accepted-authority and human-action ownership records are discovered and identities are unique. In v3 it is one repository. A future multi-repository workspace may be one authority domain without changing identity or replay semantics; references are always resolved within their containing domain.

Applicability is a closed structural union owned by immutable `ProposedScopeDescriptor` (`scope.json`): exactly `{"mode":"all"}` or `{"mode":"keys","keys":[...]}`. `mode: "all"` means universal applicability within the containing authority domain and has no `keys` member. `mode: "keys"` requires a non-empty, unique, UTF-8-byte-sorted list of exact opaque strings. No key is reserved; keys have no hierarchy, prefix, glob, regex, path, or semantic-English behavior. Readers reject unknown fields, empty/duplicate/unsorted keys, and fields inconsistent with the selected mode.

Every authority-bearing operation uses a persisted immutable `ProposedScopeDescriptor`, defined by `core/schemas/v3/scope.json` as contract `applicability-scope/1`. Its closed canonical JSON fields are `protocol_version: 3`, `scope_contract`, `origin_run_id`, `scope_id`, exact controller-proposed `requirements` text, and `applicability` using the closed union above. The controller publishes it before the human gate under `.kapisch/v3/authority/scopes/`, addressed by SHA-256 of canonical JSON for `{origin_run_id, scope_id}`; same identity/same bytes is idempotent, same identity/different bytes blocks. Its reference is `{origin_run_id, scope_id, sha256}`. The exact descriptor digest is SHA-256 of its canonical bytes. Its existence alone is never approval or authority.

For initial advisory acceptance or initial plan approval, the persisted proposed descriptor supplies applicability only to construct and present exact `GateApprovalPayload` and candidate authority basis. That pre-gate census authorizes no work, effects or other gate. The human approves the exact descriptor digest through the payload. For a repository decision, `GateApprovalRecord` proves that human approval but only the subsequent `AcceptanceRecord` makes the decision repository authority. For a plan, `GateApprovalRecord` is the durable human-approval commit; the checked `PlanRef` / promotion state is published afterward. Subsequent authoritative graph-free work reloads the exact approved descriptor through its committed acceptance or plan-approval chain; it requires no graph. For milestone work, the descriptor supplies only domain applicability; existing graph and per-node scope contract remains separate and required for node authorization. Descriptors are never caller-supplied. A changed descriptor creates a new identity/revision and requires fresh approval.

For accepted authority applicability `A` and validated consuming work applicability `W`, `applies(A,W)` is true when `A.mode == "all"`; otherwise `A.mode == "keys"` and an exact key is shared. A consuming `W.mode == "all"` denotes every key in its authority domain and therefore shares every non-empty keyed applicability set. Thus `all` authority applies to all work in its domain; keyed authority applies only through exact key membership, never string interpretation.

### 30.2 Immutable acceptance records

A committed acceptance record is the authority source of truth; producer-run state is optional provenance/reference only. Losing, rolling back, archiving or deleting that run does not revoke a surviving valid acceptance record.

Committed acceptance identity is `(origin_run_id, snapshot_id)` within its authority domain. `decision_id` is qualified by that identity. Identity is distinct from content digest. A same-identity/different-bytes collision blocks; records are never overwritten. The exact canonical-byte SHA-256 is external to the acceptance envelope and is required on every cross-record reference.

The committed acceptance namespace is `.kapisch/v3/authority/acceptances/`. The filename is lowercase hex SHA-256 of canonical JSON for `{origin_run_id, snapshot_id}`; the file contains and validates the full identity. The generic human-approval namespace is `.kapisch/v3/authority/gate-approvals/`, addressed by the immutable `approval_id` key defined in §30.2; every acceptance or checked plan reference names an exact approval ID and record digest. Human-action claims and scope descriptors use identity-derived paths over their complete identity objects. These are identity-addressed records, not an authoritative inventory. Discovery scans committed records directly; no mutable inventory, journal, or stored active-head pointer exists. Any transient index is disposable and must reconstruct the same validated result.

`canonical_json(value)` is UTF-8 JSON with object member names sorted by Unicode scalar-value order, `ensure_ascii=false`, compact `,` and `:` separators, no NaN/infinity or duplicate object keys, and exactly one terminal LF byte. Strings are not Unicode-normalized. SHA-256 is computed over these exact bytes. For `applicability`, `mode: "keys"` lists are unique and sorted by UTF-8 byte order; `mode: "all"` forbids `keys`. Every dependency/reference array is unique and sorted by lexicographic comparison of each entry's complete `canonical_json` bytes; readers reject unsorted or duplicate arrays rather than silently normalizing them.

The exact closed `GateApprovalPayload` is owned by `approval.json`. Common fields are `{protocol_version: 3, gate_contract: "human-gate/1", run_id, gate_id, identity: {kind, id}, scope_digest, gate_kind, subject}`; all are required and unknown fields are rejected. `identity.kind` is `decision`, `plan`, or `effect` according to gate kind. `repository-decision` subject is exactly `{acceptance_contract, origin_run_id, snapshot_id, decision_id, decision, scope_ref, applicability, bundle_digest, source_dependencies, authority_basis, amends, supersedes}`. `scope_ref` is `{origin_run_id, scope_id, sha256}` and its `sha256` must equal common `scope_digest`; source dependencies are sorted unique `{path, sha256}` refs; authority basis is the sorted unique §30.5 `AuthorityBinding` array; relationships are sorted unique qualified decision refs `{origin_run_id, snapshot_id, decision_id, sha256}`. The `plan-approval` subject is exactly `{plan_ref, plan_sha256, authority_basis}`, where `plan_ref` is exactly `{plan_id, path}`, `plan_sha256` is the exact retained plan-byte digest, and `authority_basis` is the complete sorted unique currently governing §30.5 binding array; common `scope_digest` binds approved scope. The `side-effect-permission` subject is exactly `{effect_identity, effect_classification, effect_request_sha256}`; identity/classification values are non-empty strings owned by the later-stage effect-request producer. Each gate kind has a distinct closed subject object; no subject field may be omitted or added.

Compute `approved_target_sha256 = sha256(canonical_json(GateApprovalPayload))` for every supported gate. `approval.json` generalizes the existing approval-record schema into one closed `GateApprovalRecord` for every authoritative human gate; no plan-specific approval schema is created. Receipt-backed `human_authority` is `{kind: "host-action", claim_ref: {identity: {session_namespace, session_id, action_id}, sha256}}`, an exact reference to the `HumanActionClaim` holding the host receipt and target. Externally supplied evidence uses `{kind: "external-artifact", path, sha256}` to exact retained artifact bytes and creates no action claim. The gate-approval publisher is sole producer of immutable `approval_id` and `GateApprovalRecord`; `approval_id` is `ga-` plus lowercase hex SHA-256 of `canonical_json({run_id, gate_id, identity, approved_target_sha256})`, so an exact target has one recoverable approval path. The record is published without replacement at `.kapisch/v3/authority/gate-approvals/<approval_id>.json`. Exact same-ID/same-bytes recovery is idempotent; different bytes at occupied identity block. Its digest is SHA-256 of exact canonical record bytes. This record proves human approval only; it does not create repository authority or enable an unsupported effect.

The immutable repository-decision `AcceptanceRecord` has exactly `{acceptance_contract, origin_run_id, snapshot_id, gate_approval_ref}`, where `gate_approval_ref` is `{approval_id, sha256}` for the exact committed `GateApprovalRecord`. The GateApprovalRecord's payload/evidence, the AcceptanceRecord's exact bytes, and any optional producer-run backlink have distinct digests; no self-reference or circular hash exists.

All required evidence must survive independently of producer-run mutable storage. Reuse the existing immutable retained CoreBundle at `.kapisch/v3/bundles/<sha256>.json`; do not make a duplicate when that store supplies exact bytes and its retention follows every surviving acceptance reference. Apply the same reuse rule to other already-retained immutable evidence. A live governing-source locator and its observed digest are separate from the retained historical binding: current-byte changes stale downstream authority but do not rewrite or erase historical acceptance.

An acceptance reference is `{origin_run_id, snapshot_id, sha256}` and is domain-relative. Decision references additionally name `decision_id`. The namespace path is derived from identity; references bind both identity and exact bytes. Missing, changed, malformed, ambiguous or unresolvable referenced records block. A committed record with malformed/unknown fields or unsupported contract cannot be skipped on the basis of untrusted scope fields.

### 30.3 Relationship semantics

Every relationship targets an earlier committed record in the same authority domain and binds its exact qualified identity and record digest. Reject missing/mismatched targets, self-links, duplicate targets, cycles, and a target present in both arrays. Records are immutable; old records do not refer forward to future records.

`amends` is additive only. It never replaces, patches, or partially overrides its predecessor. Both remain active where both apply. A semantic conflict is not resolved by order or precedence; controller/architect must obtain a new human-approved decision with valid full-coverage `supersedes` edges for every conflicting active predecessor. Core validates graph/coverage and does not infer semantic conflicts from prose.

`supersedes` is full-coverage replacement under the structural applicability union. An `all` predecessor requires an `all` successor. A `keys` predecessor with set `P` is covered by an `all` successor or a `keys` successor whose set `S` satisfies `P ⊆ S`. Additional successor keys are allowed; dropping any predecessor key is invalid. A valid successor makes each targeted predecessor inactive globally while preserving it as immutable history. No partial/per-work supersession or implicit cascading is allowed. A separately additive amendment to a superseded record remains active unless explicitly superseded itself.

For deterministic single-successor resolution, a supersession may target only a currently active predecessor. The repository lock serializes publishers: after one valid successor commits, a competing successor naming that now-inactive predecessor blocks. One successor may supersede multiple active predecessors if it independently covers each. Additive amendments do not retire or compete with one another merely by sharing a predecessor. These structural rules do not create prose precedence.

### 30.4 Human-action ownership and publication

Every receipt-backed authoritative human gate first uses one gate-neutral immutable `HumanActionClaim` keyed by `(session_namespace, session_id, action_id)` within the authority domain. The host adapter supplies opaque non-empty `session_namespace` as factual provenance; it is stable across process restart for that host session identity domain and is not derived from run, gate, target, profile, or controller memory. Core does not interpret or synthesize it.

The exact `GateTarget` is `{run_id, gate_id, identity, target, scope_digest}`. It equals the corresponding `GateApprovalPayload` fields, and `target` is exactly `approved_target_sha256`; `scope_digest` is exactly the referenced `ProposedScopeDescriptor` digest. The retained host-produced receipt must itself bind these exact values. The closed `HumanActionClaim` is `{protocol_version: 3, claim_contract: "human-action-claim/1", identity: {session_namespace, session_id, action_id}, receipt: <exact ObservedHumanAction object>, gate_target: <exact GateTarget>, approved_target_sha256}`. Its identity must equal the receipt identity; all gate-target fields and target hash must equal fields observed in the receipt. The receipt is retained as the exact canonical object from the host, not rebuilt from controller fields. Its committed path is `.kapisch/v3/authority/human-actions/<identity-key>.json`, where `identity-key` is lowercase hex SHA-256 of `canonical_json({"session_namespace":…, "session_id":…, "action_id":…})`. The claim's exact digest is SHA-256 of its canonical bytes.

`GateApprovalRecord.human_authority` is exactly one of `{kind: "host-action", claim_ref: {identity: {session_namespace, session_id, action_id}, sha256}}` or `{kind: "external-artifact", path, sha256}`. For external human-authored evidence, no host identity or synthetic claim is created. The exact canonical `external-human-approval/1` artifact is retained at its immutable artifact path and contains exactly `protocol_version`, `run_id`, `gate_id`, `identity`, `decision: "approve"`, `target: approved_target_sha256`, and `scope_digest`. Its exact bytes are digest-bound by the external-artifact reference; validators parse those bytes and compare every `GateTarget` field and target hash with the reconstructed `GateApprovalPayload`. A controller-written wrapper cannot turn unrelated bytes into human approval.

The `approval.json` schema owns the closed `GateApprovalPayload`, generic `GateApprovalRecord`, subject union and `human_authority` tagged union; `human-action.json` owns `HumanActionClaim` and its closed receipt projection. `snapshot.json` owns the global immutable `AcceptanceRecord` envelope. The schemas reject unknown fields and missing/duplicate identity bindings.

First durable `HumanActionClaim` publication occupies the action identity. Exact same identity and exact same receipt/target/claim is idempotent; any changed run, gate, decision/action ID, target, scope, payload or receipt under that identity blocks. An orphan claim remains occupied after process crash but never approves a gate, creates repository authority, or implies acceptance. Removing a run does not release the claim. The `GateApprovalRecord` must name the exact claim reference for receipt-backed approval; only that record establishes that the payload received human approval. For external evidence, its `GateApprovalRecord` references the retained artifact directly and no claim is generated. Reuse the claim primitive for repository-decision acceptance, plan approval, side-effect permission and every receipt-backed authoritative human gate. Claims are anti-replay/ownership evidence only, not an authority inventory or ordered journal. External human-authored artifact evidence has no host action identity and receives no synthetic claim.

### Plan approval publication, recovery and current eligibility

Publish in this order under repository serialization:
