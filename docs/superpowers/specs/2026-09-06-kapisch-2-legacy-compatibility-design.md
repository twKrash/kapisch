# KAPISCH 2.0 Legacy Profile Compatibility Design

**Date:** 2026-09-06  
**Status:** Approved in-chat; awaiting written-spec review  
**Target release:** KAPISCH 2.0.0

## Summary

KAPISCH 2.0.0 makes an intentional compatibility break for locally managed
profile/setup state created before the new state format. It does not migrate,
rewrite, recover, or delete legacy state automatically.

A profile is KAPISCH-managed only when its companion state record declares the
current installer-state schema and all identity, scope, path, provenance,
routing, and digest bindings verify. Structurally recognizable legacy state is
reported with exact affected paths and manual backup/removal/reinstall guidance.
Unrecognized or contradictory state fails closed as a collision.

The runtime contract is versioned independently from plugin semantic versions.
Future KAPISCH 2.1 and later releases can continue using the same installer-state
format without any code that compares against or prints `2.0`.

## Goals

- Establish KAPISCH 2.0.0 as a clean boundary for local profile/setup state.
- Remove automatic compatibility with pre-boundary profile records and switch
  transactions already present on `main`.
- Do not merge or recreate PR #35's frozen 1.0.1 fixtures, role-specific digest
  allowlist, or automatic migration behavior.
- Preserve explicit ownership, user-drift, collision, locking, concurrency,
  rollback, and atomic current-update protections.
- Keep the six logical role/profile identities stable.
- Support deterministic fresh installation and explicit current-format updates.
- Give legacy users precise manual remediation without granting the installer
  destructive cleanup authority.
- Work consistently on Linux, WSL, and native Windows Python.
- Make the supported state machine understandable without access to KAPISCH 1.x
  source trees or exact historical bytes.

## Non-goals

This change does not redesign:

- role semantics or the six role identities;
- profile-set names or workflow authority;
- orchestration, controller, or harness architecture;
- durable run manifests, controller-view versions, or their migration tools;
- validator compatibility for durable run evidence;
- marketplace architecture or unrelated CLI behavior;
- plugin removal behavior owned by Codex;
- automatic cleanup or migration of user files.

No new dependency or CI job is required.

## Compatibility Boundary

### Release boundary versus state-format boundary

KAPISCH 2.0.0 is the product release that introduces the break. Runtime state is
not keyed to that release number.

New managed profile records declare:

```toml
profile_state_version = 1
```

The implementation uses named constants such as
`CURRENT_PROFILE_STATE_VERSION`; it does not compare records to plugin versions
and does not hardcode `2.0` in diagnostics. Compatible future plugin releases
continue using profile-state schema 1 until the schema actually changes.

The existing switch-journal schemas 1 and 2 were both produced before this
boundary. The new implementation writes and recovers only switch-journal schema
3 through a named `CURRENT_SWITCH_JOURNAL_VERSION` constant. Journal schema
numbers remain independent of plugin semantic versions and profile-state schema
numbers.

### Supported state

KAPISCH supports:

- completely absent selected profile/state pairs;
- profile/state pairs created in profile-state schema 1 whose ownership bindings
  verify;
- switch-journal schema 3 whose shape, paths, and digests verify;
- compatible future plugin versions that continue to use those formats.

### Unsupported legacy state

KAPISCH does not support automatic mutation or recovery for:

- profile records without `profile_state_version`;
- profile records declaring an older profile-state version;
- switch-journal schemas 1 or 2;
- switch preparation files declaring journal schema 1 or 2;
- historical absolute template-cache provenance accepted only for old records.

No old generated bytes or hardcoded historical digests participate in this
boundary.

A missing/older marker can classify state as legacy only for diagnostics. It
never establishes ownership.

### Unknown state

A newer profile-state or journal version is unsupported but is not labeled
legacy. Malformed, unreadable, symlinked, contradictory, or incompletely bound
objects are collisions or inconsistent state. The installer never guesses that
they are KAPISCH-owned.

## Current Profile-State Record

A current record contains at least:

```toml
profile_state_version = 1
template = "kapisch-<role>.toml"
template_sha256 = "<normalized canonical template digest>"
installed_profile = "<exact target path>"
scope = "project-or-user"
profile_set = "balanced-or-quality-or-budget"
profile_identity = "kapisch-<role>"
installed_model = "<resolved model written to the profile>"
installed_model_reasoning_effort = "<resolved effort written to the profile>"
installed_sha256 = "<installed profile digest>"
```

The two resolved-routing fields preserve the runtime values installed for the
recorded profile set. They allow a future routing-table change to be classified
as an available managed update rather than as a collision, while still catching
a contradictory state edit.

The template field is exactly the stable template filename. Absolute Unix or
Windows plugin-cache paths are not current provenance. Moving from one plugin
cache location to another remains supported because the state does not bind to
the cache location.

## Ownership Rules

KAPISCH establishes current managed ownership only when all of these conditions
hold:

1. The target and record are regular files, not symlinks.
2. Both files are readable UTF-8 TOML.
3. `profile_state_version` equals the current supported schema.
4. The target's `name` is the expected `kapisch-<role>` identity.
5. The record's identity equals that same value.
6. The record's installed path equals the exact selected target path.
7. The record's scope equals the selected scope.
8. The template value equals the canonical template filename.
9. The profile set belongs to the current closed profile-set catalog.
10. The target's parsed model and effort equal the resolved values stored in the
    record.
11. The record's template and installed digests are well-formed SHA-256 values.
12. Adjacent profile identity and filesystem checks find no collision.

A pathname, filename, internal `name`, historical template path, or digest by
itself is insufficient.

The local state is not a cryptographic trust boundary. The bindings protect
against accidental collision, drift, stale state, and destructive guessing; they
do not claim to resist a user who deliberately edits both a profile and its
companion state consistently.

## Drift and Update Rules

Ownership, user drift, and desired updates are separate classifications:

- **Undrifted:** the target's actual digest equals the record's
  `installed_sha256`, and its model/effort equal the record's resolved routing.
- **User drift:** the actual target digest or recorded installed routing no
  longer agrees with the recorded installation.
- **Template drift:** the normalized current canonical template digest differs
  from the record's template digest.
- **Update available:** the current desired generated digest or normalized
  template digest differs from the verified installed record.

A current, undrifted profile can be updated to current desired bytes with
`--install --replace-managed`, including when the selected profile set is
unchanged. A routing-table change is therefore a supported update; the
implementation does not need old routing tables or generated files.

User drift is reported during inspection and is never overwritten. Any explicit
replacement attempt against a drifted profile exits with failure and leaves all
selected files unchanged.

## Installation State Machine

Classification happens for every selected role before any new install or update
is committed. `--all` is all-or-nothing for new operations.

| State | Inspection | `--install` | `--install --replace-managed` |
| --- | --- | --- | --- |
| Fresh: profile and record absent | Exit 0; report `not-installed` | Create deterministic profile and current record | Same fresh-install behavior |
| Current, undrifted, already desired | Exit 0; report current | Exit 0; no mutation | Exit 0; idempotent, no mutation |
| Current, undrifted, update available | Exit 0; report explicit replacement action | Exit 0; no mutation | Atomically update profile and state |
| Current with user drift | Exit 0; report drift | Exit 0; no mutation | Exit 2; reject replacement |
| Structurally recognizable legacy | Exit 2 with remediation | Exit 2; no mutation | Exit 2; no mutation |
| Ambiguous/unrecognized collision | Exit 2 with precise reason | Exit 2; no mutation | Exit 2; no mutation |
| Partial/inconsistent state | Exit 2 unless it is valid current transaction recovery | Same | Same |

A single-role installation is a supported state; absent unselected roles are not
inconsistent.

Under `--all`, wholly absent pairs can be installed alongside current,
already-desired pairs. Mixing fresh pairs with pairs that require replacement
remains rejected. The user updates existing roles first and then completes the
catalog, preserving the existing narrow transaction model.

Mixed current and legacy pairs reject the entire selected operation without new
mutation.

## Legacy Recognition Without Migration

A selected role is recognizable as legacy only when:

- the expected target and state paths both exist as regular files;
- both parse successfully;
- the target identity is the expected `kapisch-<role>`;
- the record's identity, scope, and installed path agree with the selection;
- `profile_state_version` is absent or older than the current format.

The classifier does not compare historical template paths, profile-set routing,
profile bytes, template digests, or installed digests. These fields are
unnecessary because recognition grants only an error message.

If either pair member is absent, parsing fails, bindings disagree, or a symlink
is present, the state is partial, inconsistent, or ambiguous rather than safely
recognizable legacy.

## Transaction State

### Current schema 3

A schema-3 journal is owned current transaction state only when:

- its status and entry set have the exact supported shape;
- every role/kind pair is unique and known;
- every destination, backup, staging, and random-token recovery path derives
  exactly from the selected root and role;
- every digest is well formed;
- recovery checks actual destination/backup/staging bytes against the recorded
  digests before mutation.

A valid current journal may be recovered under the setup lock before ordinary
profile classification. Recovery is reported explicitly. Prepared transactions
roll back; committed transactions complete verified cleanup. External edits and
unrelated files remain preserved.

A schema-3 `.profile-switch.prepare.tmp` without a published journal keeps the
existing under-lock cleanup behavior. This compatibility reset adds only a
version gate before that path: schema-1/schema-2 preparation files are rejected
without mutation.

### Legacy and invalid fixed transaction state

Journal schemas 1 and 2 and preparation files declaring schema 1 or 2 are
reported as unsupported legacy transaction state and are not recovered,
rewritten, or deleted.

Malformed, unreadable, symlinked, or newer-version files at the existing journal
or preparation paths fail closed as collisions. This boundary does not add
global orphan-artifact discovery, sibling-directory globbing, or new filesystem
hardening architecture.

The schema-1 deterministic recovery pathname and its legacy prefix-ownership
fallback are removed. Current schema 3 retains only random-token recovery paths
bound by the validated journal.

## Mutation Rules

- Inspection is read-only unless a valid current schema-3 transaction requires
  explicitly reported recovery.
- Legacy rejection itself performs no filesystem mutation.
- A failure in any selected role prevents every new selected-role installation
  or update.
- Ordinary `--install` never overwrites an existing profile.
- Explicit replacement is permitted only for fully verified current ownership
  with no user drift.
- Current updates continue to stage all desired bytes and state before
  replacement, verify concurrent state, preserve backups, journal progress,
  verify final paths/identities/digests, and roll back or finish cleanup using
  the current journal.
- The installer removes only artifacts proven to belong to the current
  transaction. It never deletes a file solely because its pathname resembles a
  KAPISCH artifact.

## Diagnostics and Manual Remediation

A recognizable legacy profile rejection exits 2 and emits machine-readable,
actionable output equivalent to:

```text
status=unsupported-legacy
error=unsupported legacy KAPISCH profile state was detected
modified=false
legacy_profile=<exact path>
legacy_state_record=<exact path>
action=back up and manually remove the listed legacy files, then reinstall
guidance=<installed plugin root>/docs/compatibility.md#legacy-profile-cleanup
```

The runtime message is release-version-neutral. The compatibility document
explains that KAPISCH 2.0.0 established the boundary.

Catalog diagnostics enumerate every safely recognized affected role. Legacy
transaction diagnostics list the exact fixed journal or preparation path that
triggered refusal; they do not parse or follow legacy entry paths.

Malformed and ambiguous cases use collision/inconsistent-state output rather
than claiming legacy ownership. Python tracebacks are not part of the normal
user contract.

### Documented cleanup procedure

The compatibility documentation provides POSIX and PowerShell examples. WSL
users follow the POSIX procedure. The procedure requires the user to:

1. stop concurrent profile setup processes;
2. run inspection and record the exact listed paths;
3. back up every exact profile, record, journal, or preparation path listed by
   the installer;
4. inspect the backup and confirm the files are the installation being reset;
5. manually remove only those exact files;
6. remove now-empty KAPISCH setup directories only if desired;
7. rerun 2.x inspection and confirm a fresh state;
8. run the ordinary explicit install command;
9. inspect again and verify current state, expected identities, and no drift.

The procedure must not delete `.kapisch` wholesale because durable run evidence
can coexist elsewhere. Plugin uninstall and optional profile removal are
separate operations; uninstalling a plugin does not prove profile ownership.

No automatic cleanup command or `--force` migration escape hatch is added.

## Deterministic and Cross-platform Behavior

Template processing decodes UTF-8 and normalizes CRLF and CR newlines to LF
before canonical validation, canonical template hashing, rendering, and desired
profile hashing. Equivalent LF and CRLF source templates therefore produce the
same installed bytes and digests.

This behavior removes checkout newline conventions from current profile
ownership and update decisions. It does not require frozen profile fixtures or a
new `.gitattributes` rule.

The existing `.gitattributes` rule for
`plugins/kapisch/tests/kapisch_validation/fixtures/**` remains because those
unrelated durable-validator fixtures still have exact-byte digest contracts.

Native Windows Python 3.11 profile/setup and portable-package CI remains a
required gate. A separate manual native-PowerShell live acceptance run is not
required. Linux and WSL use POSIX behavior; WSL paths are treated as Linux paths.

## Compatibility Guarantees

KAPISCH guarantees after this change:

- stable six-role profile identities and paths;
- deterministic, newline-normalized fresh profiles;
- current-schema ownership across compatible plugin releases;
- explicit, digest-verified managed updates;
- user-drift and unrelated-file preservation;
- fail-closed handling when ownership is uncertain;
- actionable legacy diagnostics without historical byte knowledge;
- unchanged durable-run compatibility outside profile setup.

KAPISCH does not guarantee:

- automatic migration from legacy profile/setup state;
- automatic deletion of legacy user files;
- recovery of old transaction schemas;
- ownership inferred only from historical filenames;
- permanent support for every installer-state schema.

Any future proposal to add automatic legacy profile migration requires a new,
explicitly approved design. It must not enter as an incidental fixture, digest
allowlist, or compatibility helper.

## Acceptance Criteria

The design is implemented when all of the following are true:

1. Shipped metadata identifies KAPISCH 2.0.0 consistently.
2. Fresh installations write current, release-independent profile-state records.
3. Current undrifted installations inspect and update correctly, including
   same-set and changed-routing updates.
4. Drift, collisions, ambiguity, and inconsistent state remain non-destructive.
5. Structurally recognizable legacy state exits with actionable, generic,
   no-mutation guidance.
6. Old profile records and journal schemas cannot be migrated or recovered by
   the installer.
7. All old profile/setup compatibility branches and tests on `main` are removed.
8. PR #35's historical fixtures, hashes, and checkout rule remain absent.
9. Equivalent LF and CRLF inputs generate identical current profile bytes.
10. Current documentation consistently explains the break and manual reset.
11. Durable-run compatibility and unrelated historical evidence remain intact.
12. Linux and native Windows CI gates pass.
