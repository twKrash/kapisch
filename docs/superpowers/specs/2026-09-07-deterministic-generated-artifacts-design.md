# Deterministic Generated Artifacts Design

**Date:** 2026-09-07

**Status:** Proposed for review

**Baseline:** `main` at `265f37c` (PR #37 merged)

**Target release for shipped behavior:** KAPISCH 2.1.0

## 1. Status and scope

This document defines determinism for files and machine-readable output generated by KAPISCH. It is an architectural specification, not an implementation plan, and makes no runtime change by itself.

In scope:

- generated managed profiles and their current ownership records;
- managed-profile switch transaction artifacts;
- durable run manifests, state, handoffs, delegation records, reviewer invocations, compact outcomes, and knowledge records;
- derived controller views and optional rendered state;
- migration, benchmark, validator-output, portable-package, and fixture boundaries where they affect generated bytes;
- canonical serialization, ordering, path, newline, digest, identifier, timestamp, compatibility, rewrite, and cross-platform rules;
- behavioral acceptance requirements.

This design preserves KAPISCH 2.0.0's managed-profile compatibility reset. It does not make old profile state current, infer ownership from historical bytes, or alter historical durable-run compatibility.

## 2. Context and current behavior

KAPISCH has three persistence domains with different authority and retention rules:

1. `.kapisch/runs/<task-id>/` contains durable execution and review evidence. It is authoritative where the workflow contract says so and is not a cache.
2. `.kapisch/cache/` is derived, revision-bound, and deletable. No implemented cache writer is in the current determinism surface.
3. `.kapisch/local-state/` contains machine-local runtime state. It is not durable workflow evidence or canonical project knowledge.

Current generated output is already partly deterministic:

- `setup_profile.py` decodes templates as UTF-8 and normalizes CRLF and CR to LF before validation, template hashing, profile rendering, and installed-profile hashing.
- Role iteration uses the fixed `ROLE_CATALOG`; adjacent profile enumeration and collision reporting sort discovered TOML paths.
- Profile-state and switch-journal writers use explicit field order and UTF-8/LF output.
- `canonical_toml.render_toml` quotes keys and strings, sorts nested maps, orders root keys through an explicit prefix plus lexical remainder, rejects unsupported values and non-finite floats, emits UTF-8, and appends one LF.
- `render_controller_view.py` uses random temporary filenames for safe atomic publication while publishing deterministic view/state bytes.
- `controller_view.py` constructs a bounded projection, sorts predecessor nodes by sequence and attempts by ID, and compares the persisted view to an expected canonical byte sequence.
- state node-membership lists and review-scope lists are validated as sorted and unique;
- next-node selection uses minimum `(sequence, id)` and does not depend on filesystem or completion order;
- validator findings are sorted before text or compact JSON output;
- benchmark JSON output sorts object keys and unmatched record identities;
- raw artifact readers open in binary mode where supported and decode UTF-8 explicitly.

Current output is not uniformly deterministic:

- controller-authored durable TOML is governed by strict semantic schemas but has no single enforced write boundary;
- artifact-specific root-field and collection ordering is distributed across prose, validators, fixtures, and individual writers;
- natural-language plans, reports, contexts, and observed runtime data are intentionally variable;
- profile records and switch journals embed native absolute paths;
- locks and recovery staging contain PIDs or random tokens;
- exact evidence digests intentionally distinguish CRLF from LF and any other byte change;
- existing valid durable TOML may use arbitrary TOML formatting and key/table order;
- validator error paths contain the supplied filesystem location and therefore relocate differently;
- legacy durable migration copies bytes rather than canonicalizing them.

The existing `canonical_toml.py` and controller-view code establish a useful narrow boundary. This design extends that idea without introducing a generic serialization framework or turning the validator into a workflow runtime.

## 3. Problem statement

KAPISCH needs a contract under which generated canonical artifacts are reproducible for the same semantic inputs, same artifact schema, same KAPISCH version, and same logical operation.

Where the artifact class supports the guarantee, output must be independent of:

- repeated execution;
- Python dictionary/set/hash iteration behavior;
- filesystem enumeration order;
- checkout root or worktree location;
- Linux versus native Windows path syntax;
- LF versus CRLF source checkout differences when newline is not semantic;
- locale, timezone, process environment, and current working directory;
- atomic-write temporary names and incidental process state.

Determinism must not erase real facts. Independent attempts need distinct identities; event times must remain truthful; Git revisions and observed runtime results may differ; exact returned evidence must retain its bytes; transaction recovery needs machine-local paths and process metadata.

The design must therefore specify both the equality domain and the exclusions. "Deterministic" never means replacing variable facts with fabricated constants.

## 4. Definitions of determinism

### 4.1 Semantic determinism

Given the same normalized semantic inputs, schema/version, and logical operation, KAPISCH constructs the same logical artifact data.

Semantic equality is artifact-specific. A dependency set is equal regardless of input enumeration order. A verification command sequence is not equal when its order changes. Two independent reviewer attempts are not the same logical operation merely because their prompts match.

### 4.2 Serialization determinism

Given the same canonical logical artifact data, the canonical encoder emits exactly the same byte sequence.

Serialization determinism covers encoding, escapes, scalar spelling, key order, collection order, whitespace, and final newline. It does not promise that distinct runtime events produce equal logical data.

### 4.3 Cross-platform determinism

For canonical artifacts whose logical data excludes machine-local facts, supported Python 3.11 execution on Linux and native Windows emits byte-identical output.

Native filesystem containment is evaluated before serialization. Persisted canonical paths use the path rules in section 11, not `str(Path)`.

### 4.4 Regeneration determinism

A derived artifact regenerated from the same authoritative input snapshot emits the same canonical bytes. "Same snapshot" includes exact bytes when an existing digest contract intentionally binds exact source bytes.

Deleting and rebuilding a derived artifact must not create new IDs, timestamps, revisions, or other facts.

### 4.5 Relocation determinism

Moving a repository or worktree does not change canonical durable-run bytes when all persisted path values are repository-relative or run-relative.

Machine-local profile ownership records and switch transaction state are exempt because the selected native target path is part of their safety contract. Validator diagnostics are also exempt because their displayed path identifies the inspected location.

### 4.6 Exact-byte evidence

Some representations are semantically significant because an existing digest binds their exact persisted bytes. For these inputs, alternate formatting or newline bytes are not equivalent, even when a parser would produce equivalent text or TOML.

This category includes reviewer results, detailed reports/evidence referenced by a digest, Git command output, installed profile bytes, transaction originals/backups, and byte-preserved legacy runs.

## 6. Sources of current nondeterminism

### 6.1 Enumeration and iteration

Potential sources are filesystem directory iteration, glob/rglob results, unordered sets, dictionary construction order, extension maps, and records assembled from multiple validators. Existing writers sometimes sort these inputs, but no shared rule covers every artifact.

Filesystem discovery order is never semantic. A writer must transform discovered entries into validated logical identifiers or normalized relative paths, then sort by the artifact's declared key before serialization.

### 6.2 Source formatting

TOML permits multiple equivalent representations: quoted or bare keys, ordinary or multiline strings, tables or inline tables, arbitrary whitespace, and arbitrary key/table order. Current readers accept many such forms. Equivalent parsed values do not imply equal source bytes.

Canonical output must therefore serialize from logical data, not patch or preserve arbitrary source formatting. Exact-byte evidence and compatibility copies are explicit exceptions.

### 6.3 Paths and roots

`str(Path)` differs by root and platform. It is correct for current profile ownership and transaction recovery because those records bind a native destination. It is incorrect for portable durable artifact references.

Current working directory must never select the bytes of a canonical path. The writer must receive an explicit repository, run, or destination root and normalize against that root.

### 6.4 Newlines and encoding

Python text APIs may translate newlines, platform tools may produce different line endings, and Git checkout attributes may rewrite text. Existing exact-byte digests expose these differences.

Canonical KAPISCH output must use binary writes of pre-encoded UTF-8/LF bytes. Exact external evidence remains byte-preserved.

### 6.5 Runtime and environment

PIDs, random tokens, runtime task IDs, external URLs, Git revisions, clock values, elapsed time, and provider metrics are real observations. Locale, timezone, `PYTHONHASHSEED`, process start directory, and unrelated environment variables are ambient noise unless an artifact explicitly records one as a fact.

Canonical encoders must not read ambient state. Callers provide all semantic values explicitly.

### 6.6 Digest domains

The repository currently uses multiple intentional digest domains: normalized template bytes, installed/raw evidence bytes, compact semantic JSON, canonical generated TOML, and raw Git command output. Treating them as one generic "content hash" would break provenance and compatibility.

Every digest field must name its byte domain in code/docs/tests. No digest is computed over a temporary pathname, filesystem metadata, native newline translation, or implicit string encoding.

## 7. Required guarantees by artifact class

| Guarantee | Canonical deterministic content | Intentionally variable durable/runtime content | Ephemeral transaction state |
| --- | --- | --- | --- |
| Semantic determinism | Required for same normalized logical input | Required only within the same identified event/record; new events may differ | Not required beyond recovery invariants |
| Serialization determinism | Required | Required for machine-readable envelopes/summaries with fixed values; prose/exact evidence excluded | Optional; current explicit field order may remain |
| Cross-platform determinism | Required unless a field is explicitly native/machine-local | Required only for portable fixed logical values; raw tool/runtime evidence excluded | Not required |
| Regeneration determinism | Required for derived artifacts | Prohibited if regeneration would fabricate or replace evidence | Recovery recreates only verified transaction-owned bytes |
| Relocation determinism | Required for durable run and derived artifacts | Required for portable references; not for diagnostics or machine-local ownership | Not required |
| Idempotent no-op | Required: no rewrite when canonical bytes and semantics are unchanged | Required after terminal persistence; stable record reused | Cleanup/recovery may mutate only verified transaction state |

A file may contain variable values and still require canonical serialization. For example, reviewer invocation IDs differ across invocations, but the same completed invocation envelope must always serialize identically.

## 8. Considered approaches

### 8.1 Local normalization in each writer

Each writer independently defines encoding, key order, collection order, path spelling, and digest timing.

- **Correctness:** attainable but depends on repeated local discipline.
- **Blast radius:** smallest initial edits.
- **Compatibility:** easy to preserve per writer.
- **Auditability:** poor; equivalent rules remain scattered.
- **Future drift:** high, already visible in manual profile/journal writers versus `render_toml` and controller-authored files.
- **Testability:** requires duplicated tests for the same byte rules.
- **Complexity:** low initially, cumulative over time.
- **Maintenance:** high because every new artifact re-decides shared rules.

This approach is rejected as the long-term contract.

### 8.2 Shared narrow canonical serialization boundary

Shared pure helpers define canonical text/TOML bytes, portable path conversion, deterministic map/scalar spelling, and digest functions with explicit domains. Artifact-specific encoders define schema field order and collection semantics.

- **Correctness:** strong; common byte invariants have one implementation while semantic distinctions remain explicit.
- **Blast radius:** bounded to real writers and encoder call sites.
- **Compatibility:** supports tolerant reads and canonical writes without schema changes.
- **Auditability:** strong; reviewers can inspect one byte grammar plus a field-order/order-semantics table per artifact.
- **Future drift:** low when new writers must select an existing primitive and declare their artifact rules.
- **Testability:** shared property coverage plus behavioral writer/CLI tests.
- **Complexity:** moderate and proportional to current writer count.
- **Maintenance:** low; no registry, plugin system, or reflection framework.

This approach is selected.

### 8.3 Canonical intermediate model for every artifact

Every artifact becomes a typed canonical object graph before an artifact-specific encoder runs.

- **Correctness:** strongest formal type boundary.
- **Blast radius:** largest; overlaps existing parser/validator dataclasses and v1–v4 compatibility code.
- **Compatibility:** harder because historical versions and exact evidence require parallel models.
- **Auditability:** mixed; types clarify shape but create another schema authority.
- **Future drift:** low inside the framework, high risk between framework and normative Markdown/validators.
- **Testability:** strong but model-heavy.
- **Complexity:** high.
- **Maintenance:** unjustified for a small standard-library plugin and risks turning Python into a workflow runtime.

This approach is rejected under YAGNI.

## 9. Recommended architecture

### 9.1 Boundary

Use a two-layer boundary:

1. **Shared canonical byte primitives** own encoding, newline, scalar spelling, map-key ordering, portable path conversion, and digest-domain helpers.
2. **Artifact-specific encoders** own allowed/required fields, root-field order, optional/default normalization, collection ordering, and semantic validation before bytes are produced.

The shared layer must remain pure and standard-library-only. It receives logical values and explicit roots; it does not inspect the clock, environment, current working directory, Git, filesystem enumeration, or runtime session.

### 9.2 Existing reuse

`kapisch_validation/canonical_toml.py` is the existing TOML primitive and remains the basis of canonical TOML behavior. `artifact_io.py` remains the binary/UTF-8 read boundary. Existing artifact-specific functions such as `render_controller_view` remain the right place for schema order and projection rules.

The architecture does not require a generic serializer class, schema registry, reflection, dependency, daemon, database, or new data format.

### 9.3 Writer ownership

- Executable repository writers—profile setup, controller-view rendering, and migrations—must pass final logical values through the applicable canonical or exact-byte boundary.
- KAPISCH controller/adapters remain sole writers of workflow handoffs and durable controller-owned artifacts. They must apply artifact-specific encoding rules before binary publication.
- The validator remains read-only. It may derive expected canonical bytes for a replaceable projection or validate byte-level contracts, but it must not repair, rewrite, dispatch, migrate, or approve.
- Roles and delegates return evidence; they do not write shared KAPISCH state.

### 9.4 Publication

Canonical generation follows:

1. collect explicit semantic inputs;
2. validate schema, value types, path containment, and collection uniqueness;
3. normalize only fields whose artifact contract declares normalization;
4. construct canonical logical data in declared semantic order;
5. encode canonical bytes;
6. compute digests over the declared byte domain;
7. validate coupled references/digests;
8. write to a same-directory temporary file in binary mode, flush/fsync where current safety requires it, and atomically replace/publish;
9. clean temporary state without changing already published bytes.

Random temporary names are allowed at step 8. They must not enter steps 4–6 or any final portable artifact.

## 10. Canonical serialization rules

### 10.1 Canonical text

Unless a stricter existing exact-byte contract applies, KAPISCH-authored canonical text is:

- UTF-8;
- no BOM;
- LF (`0x0A`) line endings;
- no CR (`0x0D`) bytes;
- exactly one terminal LF;
- no platform text-mode translation during publication.

The reviewer Git-state payload remains its existing ordered UTF-8 representation with **no trailing newline**. Canonical JSON bytes used only as a digest payload also have no trailing newline. CLI JSON/text records emitted through `print` have one trailing LF.

### 10.2 Unicode

- Preserve the exact Unicode scalar sequence supplied by semantic input.
- Do not apply NFC, NFD, NFKC, NFKD, case folding, or locale-sensitive transformation.
- Reject unpaired UTF-16 surrogate code points before publication.
- Non-ASCII characters are emitted directly as UTF-8 when TOML/JSON grammar permits.

Two canonically equivalent Unicode normalization forms remain different semantic string values. This avoids silently changing identifiers, user text, paths, or evidence.

### 10.3 Canonical TOML byte grammar

For artifacts designated canonical TOML:

- encode every key as a TOML basic quoted string;
- encode strings as one-line TOML basic strings;
- escape `"`, `\`, backspace, tab, LF, form feed, and CR with TOML basic-string escapes;
- escape remaining C0 controls and DEL as lowercase `\uXXXX`;
- encode booleans as `true` or `false`;
- encode integers as minimal base-10 text with no `+`, underscores, or leading zero padding;
- encode finite floats with the stable shortest round-tripping Python 3.11 representation;
- reject NaN and positive/negative infinity;
- reject TOML date, time, datetime, bytes, null, tuple, set, custom object, and non-string map-key values;
- encode lists with `[` and `]`, comma-space separators, and no trailing comma;
- encode nested maps as inline tables with `{` and `}`, comma-space separators, and recursively sorted quoted keys;
- encode the document as root `"key" = value` assignments, one per line;
- emit root fields in the artifact-specific schema order; optional extension namespaces follow in sorted order through their containing `extensions` map;
- emit exactly one LF after the final assignment.

Canonical writers reject unknown normative fields before encoding. Reverse-DNS extension namespaces and all nested extension keys sort by Unicode code-point order. Canonical new extension values are limited to the supported JSON-compatible scalar/list/map subset plus finite numbers; historical readers retain their existing compatibility behavior.

### 10.4 Canonical JSON

Where JSON is the specified representation:

- UTF-8, no BOM;
- object keys sorted recursively by Unicode code-point order;
- `,` and `:` separators with no extra whitespace;
- non-ASCII characters emitted directly;
- arrays preserve declared semantic order;
- non-finite numbers reject;
- digest payloads have no trailing LF;
- CLI/JSONL records append exactly one LF per record.

The existing semantic state digest continues to use compact sorted-key JSON over parsed state after removing `controller_view_path` and `controller_view_sha256`.

### 10.5 Optional and default values

- Emit every field required by the current artifact schema.
- Omit an optional field only when absent is the schema-defined logical value.
- Normalize absent or empty optional `extensions` to omission on new writes.
- Never invent TOML null. Use the literal string `unavailable` only where the existing schema explicitly defines that sentinel.
- Preserve empty required arrays as `[]`.
- Resolve defaults only when creating a current artifact whose schema owns that default. Reading v1 compatibility input must not materialize defaults back into the file.
- Distinguish integer and float TOML types; `1` and `1.0` are not normalized into each other.

## 11. Path, newline, ordering, and digest rules

### 11.1 Portable path categories

Canonical durable path fields use one of two explicit roots:

- **run-relative:** relative to `.kapisch/runs/<task-id>/`, including task reports, review artifacts, outcomes, controller view, delegation files, and source plan within the run;
- **repository-relative:** relative to repository root, including approved read/write scope and configured reviewer profile.

Canonical portable paths:

- use `/` separators;
- are non-empty and relative;
- contain no drive prefix, UNC prefix, leading `/`, NUL, empty component, `.` component, or `..` component;
- preserve component spelling and case;
- are derived from a contained native path by `relative_to(explicit_root)` and POSIX joining of its parts;
- are not produced by blindly replacing `\` in an untrusted string;
- never contain the repository/worktree absolute root.

A writer validates symlink/reparse/regular-file policy using the existing artifact-specific safety contract before path serialization. This design does not unify or weaken those policies.

### 11.2 Native machine-local paths

The following remain exact native strings:

- profile-state `installed_profile`;
- switch journal destination, backup, staged, and recovery paths;
- diagnostics that identify a local file;
- temporary filesystem paths used only during an operation.

On Windows these values may include drive letters and backslashes. They are intentionally outside relocation and cross-platform byte equality. They still use safe TOML string escaping.

### 11.3 Non-path strings

Git revisions, URLs, provider IDs, task/session references, authority references, commands, globs, and prose are not path-normalized merely because they contain `/` or `\`. Artifact schemas must identify which fields are paths.

### 11.4 Collection ordering matrix

| Collection | Canonical rule | Why |
| --- | --- | --- |
| Manifest `nodes` | Sort by `(sequence, id)` | `sequence` is approved plan order; input/container order is not a second authority |
| `nodes[].depends_on` | Sort unique IDs lexically | Existing contract says dependency order is not semantic |
| State completed/running/ready/blocked/failed IDs | Sort unique IDs lexically | Existing validator requires this |
| Review scope terminal/wave compatibility IDs | Sort unique IDs lexically | Existing validator requires sorted unique values; non-empty wave fields remain unsupported |
| Route `steps` | Sort by `(sequence, id)` | Route is ordered by explicit sequence, not discovery order |
| `nodes[].reads`, `writes`, `shared_resources` | On initial creation, normalize applicable path values, deduplicate, and sort lexically; after persistence, preserve that exact list order | Scope input is set-like, but current previous-snapshot compatibility freezes persisted list order |
| Verification commands/checks | Preserve approved/executed order | Order may affect behavior and evidence interpretation |
| `context_refs` | Preserve explicit selection/reference order | Knowledge contract makes reference order semantic |
| `delegation_ids` | Preserve route-step sequence order | It records ordered delegated substeps and remains immutable on resume |
| Assignment `reason_codes` | On initial creation, deduplicate and sort lexically; after persistence, preserve exact order | Codes are set-like at classification, but assignment fields become stable durable history |
| Assignment attempts and escalations | Preserve append/event order | History order and predecessor relationships are semantic |
| Verification evidence | Preserve command/evidence order | Compact outcome must exactly match graph evidence order |
| Batch member IDs, assignments, and outcomes | Preserve declared batch order | Contract explicitly calls these ordered members |
| Knowledge records | Preserve append/history order; stable IDs identify records; never reorder existing records | Record lifecycle/history is durable; selection order is separately explicit |
| Knowledge `applies_when` | Deduplicate and sort exact strings | Applicability clauses are a set |
| Outcome findings | Sort by severity rank `P0`, `P1`, `P2`, `P3`, then ID, summary, evidence path | Validator treats recognized finding blocks as content-equivalent regardless of report order |
| Reviewer report findings and exact result lines | Preserve returned bytes/order | Returned report is exact-byte evidence |
| Benchmark JSONL rows | Sort by `(run_id, scenario-rank, invocation, role)`; reject duplicate `(run_id, scenario, role, invocation)` identities | Persisted invocation numbers carry event order; source enumeration does not |
| Validator findings | Existing `ValidationError.sort_key` | Stable derived diagnostics |

If a future field is not listed, its schema must declare either a stable sort key or order preservation before it can claim canonical generation. "Sort where necessary" is not an acceptable rule.

### 11.5 Newline normalization matrix

| Input/output | Rule before hashing |
| --- | --- |
| Bundled managed-profile template | Decode UTF-8; CRLF→LF and lone CR→LF; hash normalized bytes |
| Generated managed profile | Render from normalized template; emit LF; hash final bytes |
| Canonical generated TOML/text | Encode canonical LF bytes; hash final bytes |
| Reviewer/delegate/task report already persisted | No normalization; hash exact bytes |
| Git command output | No decoding/newline translation; hash exact raw command bytes |
| Legacy durable migration source/destination | No normalization; compare/copy exact bytes |
| Existing noncanonical current TOML | Parse tolerantly; do not hash a canonical substitute when existing contract binds raw bytes |
| Semantic state digest | Parse TOML, remove view-binding fields, canonical compact JSON encode, hash those JSON bytes |

### 11.6 Digest computation matrix

- **Template SHA-256:** normalized canonical template bytes.
- **Installed profile SHA-256:** exact final installed profile bytes.
- **Profile switch original/desired SHA-256:** exact original and desired destination bytes.
- **Controller-view `source_manifest_sha256`:** exact authoritative manifest bytes. This remains unchanged for v4 compatibility.
- **Controller-view `source_state_sha256`:** existing semantic compact-JSON digest excluding controller-view bindings.
- **State `controller_view_sha256`:** exact canonical controller-view bytes.
- **Report, invocation, delegation context/evidence, verification, and outcome-bound SHA-256:** exact persisted artifact bytes.
- **Git-state component SHA-256:** exact raw bytes from the commands defined in `handoffs.md`.
- **Git-state payload SHA-256:** UTF-8 bytes of the exact ordered payload with no trailing LF.
- **Benchmark or validator output digest, if later persisted:** exact canonical output bytes and an explicit schema field naming that domain.

All digests use lowercase hexadecimal SHA-256. Compute after canonicalization for generated canonical output and before no later transformation. Compute raw-byte digests only after exact evidence is durably persisted/read back.

A digest field must never silently switch domains without a schema/version change. This design makes no such switch.

## 12. Timestamps, identifiers, and ephemeral state

### 12.1 Timestamps and dates

No current normative machine-readable durable schema requires a timestamp. Do not add `generated_at`, `updated_at`, or similar fields to canonical or derived artifacts merely to record generation.

When a real event time is already required by prose/metrics or a future approved schema:

- capture it once at the event boundary;
- persist UTC RFC 3339 as `YYYY-MM-DDTHH:MM:SSZ` unless the external source's exact representation is itself evidence;
- do not recompute it during regeneration or resume;
- do not derive it from local timezone or locale;
- treat it as intentionally variable event data.

Existing handoff `date` values are event metadata and do not receive repeated-run byte equality. Derived controller views and optional state views must not introduce current-time fields.

### 12.2 Identifier classes

**Deterministic structural identifiers** derive from approved semantic structure and stable sequence:

- canonical `task_id` slug when no explicit ID is supplied;
- graph node IDs;
- delegation step IDs;
- knowledge record IDs when assigned from ledger sequence;
- fixed artifact paths derived from those IDs.

The same approved structure and collision-free namespace should derive the same structural identifiers.

**Unique event identifiers** identify independent operations and must remain unique, not deterministic across operations:

- assignment and attempt IDs;
- reviewer invocation IDs;
- external fallback references;
- runtime task/session/provider operation IDs;
- route IDs when they identify a distinct route event.

Once persisted, every identifier is stable and reused idempotently for that event. Resume never generates a replacement ID for an existing planned, dispatched, completed, blocked, or failed event.

Randomness is permitted for unique event IDs only when required by their collision/provenance contract. It is never seeded from `PYTHONHASHSEED`, clock formatting, current directory, or filesystem order.

### 12.3 Ephemeral names

Atomic write, migration staging, backup, lock, and recovery names may include secure random values, PIDs, or temporary-directory roots. Their variability is allowed when:

- they remain in the same containment boundary required by atomic publication;
- ownership and cleanup are verified under existing safety rules;
- final portable artifacts contain no temporary path/token;
- final content digest excludes the temporary name and metadata;
- interruption cannot cause a partial canonical destination to be accepted.

Switch-journal recovery paths are the deliberate exception to "final artifact contains no temporary path": the journal exists only while transaction recovery is pending and is classified as transaction state, not canonical final output.

## 13. Ownership, drift, and rewrite semantics

Canonical formatting does not establish ownership.

### 13.1 Managed profiles

A profile remains KAPISCH-managed only when current schema-1 state and every identity, scope, exact installed path, template provenance, routing, digest, and adjacent-catalog check verify under the KAPISCH 2.0 rules.

- Inspection without current transaction recovery is read-only.
- A user-modified profile is drift even when its parsed TOML is semantically equivalent to desired canonical TOML.
- Canonicalization never overwrites user drift.
- Fresh install writes canonical profile and state bytes.
- An explicit `--install --replace-managed` operation may write canonical current bytes only after ownership and no-drift checks and only when a substantive desired update exists.
- Formatting-only difference is not a substantive desired update and does not authorize replacement.

### 13.2 Durable run state

Readers remain tolerant of semantically valid current-version TOML formatting.

- Resume/validation does not rewrite an unchanged manifest, state, route, invocation, outcome, or knowledge ledger solely to canonicalize it.
- A real permitted lifecycle transition may reserialize the mutable artifact canonically after semantic compatibility validation. It must preserve every immutable value and every list order or optional-field-presence distinction that current previous-snapshot compatibility treats as stable; initial-creation normalization is not retroactive authority to reorder history.
- If reserialization changes bytes referenced by another digest, the writer updates every coupled mutable digest/reference atomically in the same logical transaction.
- Immutable terminal outcomes, completed exact evidence, and completed invocation/report bindings are not rewritten for formatting.
- Existing exact manifest-byte bindings remain authoritative until a permitted semantic mutation publishes a new canonical manifest and coupled view/state.

### 13.3 Derived artifacts

`04-controller-view.toml` and optional `03-state.md` have no independent authority. Explicit regeneration may replace missing, stale, corrupt, or noncanonical derived bytes after authoritative inputs validate.

Regeneration may update the mutable state binding to the newly generated view digest. It must not change any other state meaning, create evidence, create IDs/timestamps, or repair invalid authoritative input.

### 13.4 Compatibility and migration

- Legacy byte-copy migration preserves bytes and does not canonicalize.
- v3→v4 migration creates a new destination and may canonically encode newly created v4 machine artifacts while preserving copied detailed evidence.
- Reading a historical/current compatible artifact never implies permission to migrate or rewrite it.
- A filename, canonical appearance, or digest alone never establishes KAPISCH ownership.

## 14. Compatibility and schema/version implications

### 14.1 Managed profile/setup compatibility

This design preserves:

- `profile_state_version = 1`;
- switch-journal schema 3;
- generic non-mutating diagnosis of older profile state;
- non-mutating refusal of journal/preparation schemas 1–2;
- fail-closed handling of malformed, contradictory, symlinked, unreadable, or newer state;
- explicit managed replacement and user-drift refusal;
- current schema-3 prepared rollback and committed cleanup semantics;
- no historical profile bytes or digest allowlists.

Canonical write formatting alone does not require a profile-state or journal schema bump because parsed fields and ownership meaning do not change and current readers remain tolerant. Any future change to path meaning, digest domain, ownership evidence, or recovery behavior does require a separate schema/compatibility decision.

### 14.2 Durable-run compatibility

Manifest versions 1–4, route schema 1, outcome schema 1, view schema 1, current invocation envelope compatibility, and knowledge ledger version 1 remain unchanged.

- v1–v3 runs remain readable/resumable without synthesized outcomes or views.
- v4 raw manifest and exact evidence digest domains remain unchanged.
- Legacy reviewer-profile paths remain validation-only compatibility for the existing completed/terminal cases and do not authorize new legacy-profile invocations.
- Legacy migration remains explicit and byte-preserving.
- Noncanonical but semantically valid current TOML remains readable.

A schema bump is required only if implementation changes accepted fields, field meaning, digest domain, path meaning, required ordering as semantic input, or compatibility behavior. This design's canonical-write requirement does none of those.

### 14.3 Plugin semantic version

The design document alone requires no version change.

Shipping deterministic generation across KAPISCH-owned writers is a backward-compatible workflow/runtime capability and material shipped behavior. Under `plugins/kapisch/CONTRIBUTING.md`, it requires a **minor** release, expected `2.1.0`, not a patch. A patch is reserved for a backward-compatible bug fix; this work establishes a new public generation guarantee across multiple artifact classes.

If implementation instead makes previously accepted current artifacts unreadable, changes a digest domain, or changes durable field meaning, that would exceed this design and require a new compatibility and possibly major-version decision.

## 15. Error and fail-closed behavior

Canonical generation must fail before publication when:

- a value has an unsupported type;
- a float is non-finite;
- a string contains an unpaired surrogate;
- a map key is not a string;
- a normative field is unknown or a required field is missing;
- an unordered collection contains duplicates that cannot be normalized safely;
- an ordered collection lacks its required stable sequence/identity;
- a portable path is absolute, drive-qualified, UNC, empty, ambiguous, escaping, or outside its declared root;
- a digest's input domain is unavailable or mismatched;
- a source exact-byte artifact is missing, unreadable, non-regular, invalid UTF-8 where required, or changed after preflight;
- coupled output cannot be atomically published and revalidated.

Failure rules:

1. Do not fall back to platform-default encoding, locale ordering, current directory, source formatting, or a guessed path.
2. Do not emit partial canonical destination files.
3. Preserve preexisting destinations and user data.
4. Clean only transaction-owned temporary artifacts proven by the existing ownership rules.
5. Preserve a valid recovery journal when cleanup cannot complete.
6. Report deterministic error codes/order where a CLI contract exists; include exact local paths when needed even though that makes diagnostics relocation-dependent.
7. Do not repair authoritative durable state from derived views, reports, chat, or filenames.
8. Do not classify noncanonical formatting as corruption when parsed current-version semantics are valid.

## 16. Cross-platform requirements

Supported canonical generation targets Python 3.11 on Linux and native Windows.

Required behavior:

- binary read/write for bytes participating in canonicalization or hashing;
- explicit UTF-8 decode/encode;
- POSIX-form persisted durable paths after native containment validation;
- no reliance on path separator, drive letter, current directory, default encoding, newline translation, locale collation, or local timezone;
- deterministic lexical ordering by Unicode code point, not OS filename collation;
- case-preserving paths with no platform case folding in serialized bytes;
- portable filename atom validation for artifact IDs used as filenames;
- same canonical output for fixture roots containing spaces and non-ASCII components;
- no assumption that WSL-mounted filesystem semantics equal native Linux or native Windows semantics.

Machine-local path records, lock behavior, filesystem metadata, hard-link behavior, and temporary names may differ across platforms while final portable artifacts remain equal.

### 17.1 Golden-fixture policy

Use goldens only for small public byte contracts:

- one representative canonical TOML document covering scalars, nested maps, Unicode, controls, and ordered/unordered arrays;
- one canonical text/newline case;
- one cross-platform end-to-end artifact tree or digest manifest.

Do not recreate the abandoned six-role historical-byte catalog from PR #35. Managed-profile behavior should generate from current templates and compare outputs across perturbations. Compatibility tests may synthesize minimal old structures only to prove refusal.

### 17.2 Behavioral proof requirement

At least one test per real writer class must invoke the actual public path:

- `setup_profile.main` or its CLI behavior;
- `render_controller_view.py` with a full valid v4 fixture;
- `migrate_controller_view_v4.py` for explicit conversion;
- `migrate_legacy_run.py` for byte preservation;
- controller/artifact-specific encoders followed by the full validator for new durable artifacts;
- benchmark comparison CLI for deterministic JSON.

Property tests for the shared TOML primitive supplement these tests; they do not replace them.

## 18. Rollout and compatibility strategy

1. Treat this specification as the normative determinism contract before changing writers.
2. Introduce shared byte primitives without changing accepted schemas or digest domains.
3. Add artifact-specific normalization/ordering at each actual writer boundary, preserving exact-byte exceptions.
4. Keep readers tolerant and no-op paths non-rewriting.
5. Move executable writers to canonical publication incrementally; each writer must pass its behavioral perturbation matrix before claiming compliance.
6. Add native Windows parity for representative canonical outputs. Linux-only equality is insufficient.
7. Update shipped documentation/version metadata only when behavior is implemented; target a minor release.
8. Do not bulk-reserialize existing current or historical state. Canonical convergence occurs on fresh creation, explicit migration to a new destination where already supported, or a real authorized mutation of a mutable current artifact.
9. If a rollout discovers that a required digest/path meaning must change, stop and produce a separate compatibility/schema design rather than weakening tolerant reads or silently rebinding evidence.

No canonicalization command, background migration, repository-wide rewrite, or startup repair is part of rollout.

## 19. Explicit non-goals

This design does not:

- restore automatic migration of pre-2.0 managed profiles;
- infer profile or transaction ownership from names, formatting, or historical hashes;
- recover switch-journal schemas 1–2;
- change six logical KAPISCH role identities or profile-set meaning;
- change durable manifest versions 1–4 or historical compatibility behavior;
- redesign task/milestone execution, review provenance, final readiness, or fix policy;
- make independent attempts, invocations, timestamps, revisions, URLs, metrics, or real observations deterministic;
- normalize or rewrite exact reviewer/delegate/report/Git evidence;
- add parallel execution, worktree integration, or multi-writer orchestration;
- change Pi, Hermes, Codex, or other harness orchestration;
- add a general-purpose serialization framework, new data format, dependency, daemon, database, or service;
- make Python the semantic router, scheduler, approval engine, or repair engine;
- add automatic canonical rewrite/migration of existing runs;
- redesign profile locking, filesystem containment, metadata publication, or controller-view symlink policy tracked separately by existing issues;
- implement the feature in this design phase.

## 20. Open questions and closed decisions

No unresolved design questions remain.

Closed decisions:

1. Use a shared narrow canonical byte boundary plus artifact-specific encoders.
2. Preserve all existing schema numbers and digest domains.
3. Keep current readers tolerant and writers canonical.
4. Do not rewrite unchanged files solely for formatting.
5. Treat user-modified managed files as drift, never canonicalization targets.
6. Keep profile ownership and switch transaction paths native and location-bound.
7. Keep durable-run paths portable, relative, and POSIX-form.
8. Normalize newlines only before generating canonical output, never inside exact-byte evidence domains.
9. Keep event IDs/times truthful and stable, not repeat-deterministic.
10. Permit random atomic/recovery names while prohibiting leakage into canonical final portable output.
11. Prefer behavioral perturbation tests and a few small goldens over a frozen fixture catalog.
12. Ship implemented behavior as a backward-compatible minor release; design-only documentation does not bump version.

Consciously deferred follow-up work:

- cross-process setup lock hardening (issue #23);
- broader profile filesystem containment/metadata/publication hardening (issue #25);
- controller-view symlink policy and recovery edge coverage (issue #33);
- actionable v3→v4 migration diagnostics (issue #31);
- any future cache schema and reproducible archive/package format;
- any future durable timestamp field, external-effect lifecycle, or schema/digest-domain change.

These deferrals do not weaken the determinism rules for current generated artifacts and must not enter implementation as incidental refactors.
