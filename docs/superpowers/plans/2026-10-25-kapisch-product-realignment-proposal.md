# Kapisch Product Realignment and Architecture Simplification Proposal

- **Status:** APPROVED on 25 Oct 2026.
- **Prepared against:** `main` at `fc31633effe97cb4f14df51c5256e71084bed2a9`
- **Scope:** Approved architecture direction and repository assessment only. This document does not authorize implementation, deletion, migration, commit, push, merge, release, or external-system changes.
- **Companion specification:** [Kapisch Product Realignment Design Specification](../specs/2026-10-25-kapisch-product-realignment-design.md).

## 1. Executive proposal

Recenter Kapisch on the product: human-governed, harness-agnostic orchestration of an AI-assisted software lifecycle. Kapisch should coordinate context, work orders, bounded agent attempts, parallel dependencies, evidence aggregation, independent review, explicit human decisions, and durable outcomes. It should not become a replacement Git, filesystem, agent runtime, or deployment platform.

The recommended direction is a task-first replacement for the current V2/V3 execution model, using readable files and Git plus the existing host's agent/session facilities. Keep one small active contract family. Do not read, migrate, or preserve runtime compatibility for historical V2/V3 run formats; Git retains old source history. Preserve the `kapisch-reviewer` capability and necessary installation interfaces while adapting them to portable role/lens contracts.

The architecture direction was approved on 25 Oct 2026. The remaining artifact, adapter, gate, and sequencing details are delegated engineering design responsibilities under the constraints below, not additional approval gates. Escalate only when a choice changes product intent, approved scope, human authority, security boundaries, external-effect permissions, or creates a material architectural trade-off that cannot be resolved within those constraints. This approval does not authorize implementation or repository mutations.

## 2. Product vision and scope

Kapisch coordinates work from discovery and research through requirements, architecture, implementation, verification, review, deployment decisions, and operational feedback. It helps the human and agents share context, decompose work into dependent tasks, execute independent tasks in parallel when supported, assemble evidence, and present decisions at the right points.

The human remains the decision-maker. Agent plans, task completion claims, aggregation summaries, and reviewer findings are evidence or recommendations. None becomes a human decision merely because it is persisted or labelled `complete`.

The product should make useful work portable across agent harnesses. A host supplies model invocation, sub-agent dispatch, tool execution, sessions, worktree support, and actual permission enforcement. Kapisch supplies workflow semantics, context and work orders, coordination, aggregation, review lenses, and human decision boundaries. If an adapter cannot enforce a required capability, it must say so and block or explicitly re-scope the work; it must not claim or emulate the missing guarantee.

## 3. Non-goals and scope boundaries

Do not build:

- A custom Git system or substitute for Git's code history and worktrees.
- A database or custom filesystem/persistence engine. Use ordinary files, Git, and existing host-runtime persistence for bounded state.
- A universal agent runtime, generic tool registry, or second model/session manager.
- A deployment engine. Kapisch can prepare and review deployment work and require human authorization; the target platform owns deployment execution.
- Generalized event sourcing, an elaborate artifact producer chain, a transaction coordinator, or generic recovery/reconciliation framework.
- Compatibility readers, migration of old run data, or runtime support for historical V2/V3 formats.
- Personalization or audience classification inferred from wording, role, prior interaction, or presumed expertise.

Do not resume paused Stage 5 work or treat older implementation plans as authorization for this proposal. Any superseded material remains historical in Git; this proposal does not change it.

## 4. Owner-confirmed requirements and decision status

### Confirmed by the owner

1. **Product over implementation preservation.** The proposal must optimize for user workflows and remove unnecessary complexity rather than preserve V3 as an end in itself.
2. **Harness portability.** The core task, handoff, decision, review, and outcome semantics must not depend on a particular agent host. A first release may support one real host, but adding another must not require redesigning the core. Acceptance must exercise the same logical WorkOrder through a real adapter and a lightweight test adapter.
3. **Human consultation throughout the lifecycle.** Before asking, inspect existing Context, documented decisions, contracts, ADRs, and evidence. Ask only material unresolved questions; surface assumptions and unknowns. Give the human evidence, options, trade-offs, a justified recommendation, affected scope, and the authority required. Persist answers and corrections for later stages and future sessions.
4. **Audience-neutral default.** Explain clearly without inferring expertise. A future presentation style such as `caveman` may be selected explicitly by the user; style must never change facts, evidence, options, decisions, or authority.
5. **Parallel orchestration and aggregation.** Independent work should run concurrently when the host supports it. An LLM aggregation barrier must verify every required task has a valid selected outcome, preserve references to failed, superseded, and conflicting attempts, cite evidence, and expose missing tasks and unresolved issues in a shareable report before dependent work or the next stage proceeds. The coordinator owns dependencies and transitions.
6. **Local failure policy.** For isolated local work, prefer fail-and-retry from a reliable Git checkpoint or durable handoff. Preserve failed work. Do not reset or clean a shared or user-owned worktree. Do not burden ordinary local retries with remote-effect reconciliation machinery.
7. **External-effect safeguard.** Keep special handling for genuinely ambiguous remote side effects such as pushes, merges, deployments, or non-idempotent API writes. Query the exact outcome or obtain explicit human authorization before repeating an uncertain effect.
8. **Reviewer preservation.** Preserve the actively used `kapisch-reviewer` and its valuable independent review capability. Extend reusable lenses across the SDLC, not only code changes. A review recommendation does not replace human approval.
9. **No historical-format requirement.** The owner confirms V2/V3 execution models and historical run formats are not used as live production, and does not require compatibility with them or migration of old run data. Preserve the reviewer and necessary installation interfaces. Target one active, simple contract family.
10. **Human-owned approvals.** Keep bounded authorization and meaningful human decision gates. Agent recommendations, review findings, task completion, and human decisions remain distinct.
11. **Approved architecture milestone.** This document records the approved direction. No production changes or runtime behavior changes are authorized by it; implementation requires a separately approved execution scope.
12. **Decision history and authority.** A HumanDecision is immutable evidence bound to its original question, relevant governing inputs, explicit subject, and authorization scope. Later Context snapshots may carry its answer without changing its identity. Reassess applicability after substantive governing changes; preserve old decisions and require a fresh human decision only when the existing answer or authorization no longer covers the affected work.
13. **Repository isolation.** Every worker has a distinct run/task/attempt output location, not necessarily a separate Git worktree. Read-only research and review may share a read-only repository view. Use one task-level branch/worktree only when mutable repository isolation is needed, with one designated writer. Separate worktrees are for independent tasks/PRs that need separate mutable checkouts, not a default per-worker/per-attempt rule.
14. **DAG authorization.** Human approval of a WorkOrder DAG authorizes its listed tasks within the explicit scope. Additional tasks demonstrably within that approved scope may be added without per-task approval; work outside scope requires further discussion/research and human approval.
15. **Advisory review.** `kapisch-reviewer` reports lens findings and recommendations; it never gives human approval. A WorkOrder may require successful review lenses before dependent tasks proceed. The human may accept an allowable finding or risk and authorize proceeding within scope where policy permits, but the original reviewer verdict remains unchanged; record the exception separately as a HumanDecision referencing that verdict. Generic risk acceptance cannot waive normative or security restrictions. Review/fix steps are human-directed and stay within the approved scope; no autonomous unbounded loop or separate review-approval subsystem. Scope growth requires further discussion/research and human approval.
16. **Task and attempt lifecycle.** The approved WorkOrder/DAG defines required tasks and dependencies, not future attempt IDs. Create attempt IDs as execution occurs; an in-scope retry uses a new attempt without rewriting or reapproving the DAG. A human direction to fix a failed review authorizes remediation only; dependent tasks stay blocked until a new review meets the required criteria or a separate permitted HumanDecision exception authorizes proceeding.

## 5. Approved portable architecture direction

Use a small set of readable, immutable-or-versioned records. Logical artifact families are listed here; they are not a mandate to create a schema framework or a new service for every row.

| Family                 | Minimal responsibility and ownership                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Context**            | Human-authored goals and constraints, source-linked research, assumptions, unknowns, open questions, and prior Decision references. The coordinator is the sole publisher of canonical Context snapshots; human decisions and agent findings are cited inputs, not concurrent edits. Generated analysis is not silently promoted to fact.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| **WorkOrder**          | Coordinator-authored task DAG: required task IDs and dependencies, input/context digests, scope, acceptance checks, required review lenses and pass criteria, exception policy for allowable findings/risks, expected outputs, and parallel task groups. It does not enumerate future attempt IDs. Human approval covers the DAG and its explicit scope; tasks demonstrably within that scope do not need separate approvals. An agent may propose a WorkOrder; only the coordinator publishes the canonical one.                                                                                                                                                                                                                                                                                                                             |
| **HumanDecision**      | Immutable historical evidence of a direct human answer, correction, approval, risk acceptance, or scoped external-effect authorization. It binds the original immutable question/request, relevant governing input references, explicit subject, and authorization scope. A DAG approval names the approved WorkOrder/scope and covers its in-scope tasks; consuming tasks reference that decision rather than creating per-task decisions. A permitted human exception to a review finding is a separate decision referencing the immutable reviewer report/verdict and its scope; it does not rewrite that verdict. No exception can waive normative or security restrictions. Include a WorkOrder reference only when it is part of the decision subject; discovery questions need no future WorkOrder. An agent or LLM cannot create one. |
| **Attempt and result** | Coordinator creates a fresh attempt identity and input/checkpoint reference when each dispatch occurs. Retries use new attempt IDs without changing the WorkOrder/DAG or requiring new approval when they stay within task scope. The worker/adapter reports status, output references and hashes, checkpoint, assumptions, and unresolved issues. This is a claim/evidence record, not authority.                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **Report**             | The aggregator produces a task-coverage report that references valid selected outcomes and preserves all failed, superseded, late, or conflicting attempt references; `kapisch-reviewer` produces an immutable review report with its original verdict. Reports are evidence and recommendations, not human decisions. A permitted exception is a separate HumanDecision, never a rewrite of the reviewer verdict.                                                                                                                                                                                                                                                                                                                                                                                                                            |
| **Outcome**            | Coordinator-created immutable record of accepted task/stage completion and its evidence references. It does not authorize side effects or imply human acceptance.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |

Store these in ordinary per-run/per-task/per-attempt files with shareable Markdown where useful and structured JSON for stable fields. Give each worker a unique output location. Use Git for code and durable repository history. Keep host handles, model/provider identifiers, transcripts, and session metadata in adapter-owned storage; core artifacts carry only generic IDs and evidence references. Do not add a mutable global state file: derive task state from the WorkOrder, attempts/results, reports, decisions, and outcomes.

A Git worktree is task-level isolation, not a worker/attempt requirement. Read-only research and review may share a read-only repository view. When a task needs a mutable isolated checkout, use one task-level branch/worktree with one designated writer; use separate worktrees only for independent tasks/PRs that need separate mutable checkouts.

Assign one clear producer to each durable record. A single coordinator writes canonical Context snapshots, WorkOrders, and Outcomes; workers write only their unique attempt outputs; the aggregator writes only aggregation reports; the reviewer writes only review reports; the human input boundary alone writes HumanDecisions. This is a small ownership rule, not a multi-stage authority ledger.

### Decision freshness

A HumanDecision is immutable historical evidence of a human response to an original immutable question or authorization request. Bind it to that question/request's stable ID and content, the relevant governing facts/requirements/constraints, its explicit subject, and authorization scope. Bind to a WorkOrder only when that WorkOrder is part of the subject; a discovery question created before a WorkOrder does not require one. Do not bind the decision's identity or validity to a future Context snapshot that will contain the answer.

Keep three things distinct: (1) the historical answer or correction, (2) whether that answer is currently applicable to proposed work, and (3) approval or authorization for a specific action and scope. A later Context snapshot or WorkOrder may carry the answer and cite the original Decision. That ordinary propagation does not change the Decision, stale it, or create a circular reference. A human approval of a WorkOrder DAG and its explicit scope covers listed tasks and additional tasks demonstrably within that scope; they may cite the original Decision without per-task approval. A later WorkOrder outside that approved scope, or a substantive scope expansion, is not covered and requires additional human approval.

When a later WorkOrder uses a prior Decision, the coordinator records an applicability status and reason with that reference (for example: applicable, reassessment required, no longer applicable, or superseded). This status belongs to the consuming Context/WorkOrder, not a mutation of the historical Decision. Cosmetic edits, reformatting, answer propagation, and unrelated Context additions do not by themselves invalidate applicability. A substantive change to a governing fact, requirement, constraint, question, authorization target, or scope triggers reassessment. If the prior Decision no longer covers the affected work—or applicability is unclear—block that work and request a fresh human decision. A later human Decision may explicitly reference the one it supersedes; preserve both records. Never infer a human decision or applicability from agent synthesis, aggregation, reviewer recommendations, timestamps, or a Context edit. Partial answers stay partial; an unanswered blocking question blocks its affected work. These semantics are owner-confirmed; their minimal representation in the new contract remains proposed and requires no V3 history, retained bundles, or event logs.

### Parallel orchestration and aggregation

The WorkOrder records the required task set and dependencies, not a forecast of attempt IDs. At dispatch, create an attempt ID and unique run/task/attempt output location; retries create new attempt IDs without changing or reapproving the DAG. The aggregator verifies coverage of every required task and whether each has a valid selected outcome meeting its acceptance checks. It preserves references to failed, superseded, late, and conflicting attempts rather than hiding them; missing or invalid selected outcomes block dependent work. It cites sources, lists contradictions and unresolved issues, and never invents consensus. Missing, stale, duplicate, or mismatched references make the report incomplete or invalid. A late result requires a new immutable report; it does not rewrite the previous one.

The coordinator validates coverage and references, applies the explicit dependency/acceptance policy, and alone decides whether to issue a dependent WorkOrder. A missing or failed required result blocks that transition until retried or explicitly resolved. A WorkOrder may require a successful reviewer lens before a dependent task proceeds; that lens result is evidence, never human approval. If a required lens does not pass, preserve the verdict and present it for the human to choose an in-scope fix, permitted exception, or WorkOrder update. A direction to fix authorizes remediation only; dependent tasks remain blocked until a new review report meets the required criteria or a separate permitted HumanDecision exception authorizes proceeding. Pending, interrupted, or completed-but-still-failing remediation does not release the gate. Record any exception as a separate HumanDecision referencing the verdict; do not relabel the review as a pass. The coordinator may add human-directed tasks within the approved scope without per-task approval; no autonomous review/fix loop may repeat without human direction. Work outside scope still requires additional approval.

### Failure and retry

A reliable checkpoint is a verified commit in the task-level worktree, when one is needed, or a prior complete Outcome/handoff with matching task-input digests. Choose the newest _compatible_ checkpoint by its recorded reference, not by timestamp. A mismatch is not repaired by guessing: preserve the existing worktree and ask the human if checkpoint selection would discard changes or affect scope. Preserve interrupted and failed attempts, including partial output, but never treat partial files as completed downstream input. A retry within the approved task scope gets a new attempt ID and unique output location; it does not rewrite or reapprove the WorkOrder/DAG or require additional human approval, and it does not automatically get a new worktree. Do not reset/clean shared state or create per-attempt worktrees by default.

For a remote side effect, “exact outcome” means an authoritative observation tied to the requested operation and target, or a human decision explicitly resolving or authorizing the scoped action. A missing agent report is not proof that no effect occurred. If the adapter cannot query reliably, leave the action blocked for human resolution.

## 6. Human consultation flow

At discovery, design, implementation, verification, review, deployment, and operational follow-up:

1. Read relevant Context, ADRs, contracts, repository evidence, and prior HumanDecisions before formulating a question. Do not ask for information already documented.
2. Record material unknowns separately from assumptions, with evidence/source references, impact, affected tasks, and blocking status.
3. Present the question with the known facts, source references, plausible options, trade-offs, recommendation and rationale when justified, affected scope, and required human authority.
4. Preserve the original question/request as immutable content. Capture each human answer, correction, approval, deferral, or rejection in an immutable HumanDecision bound to that question, its relevant governing inputs, explicit subject, and authorization scope. Include a WorkOrder reference only when the human decision is about that specific WorkOrder. An answer to a discovery question may precede any WorkOrder.
5. Later Context snapshots and WorkOrders may carry the answer and cite its original Decision; do not bind the Decision to those future containers or mutate it during propagation. When a later work item relies on it, record current applicability separately. Reassess if substantive governing facts, requirements, constraints, question, target, or scope changed; cosmetic changes, ordinary propagation, and unrelated Context additions do not automatically require reapproval. An in-scope task may rely on an existing DAG/scope approval by reference; if the answer or authorization no longer covers the work, request a fresh human decision. Preserve superseded or no-longer-applicable decisions with explicit references and status.

A carried-forward answer alone is not approval. A DAG approval covers tasks within its explicitly approved scope, so no per-task approval is needed. If research or execution indicates work is outside that scope, pause, present evidence and options, conduct any needed additional discussion/research, and obtain human approval before expanding the WorkOrder or acting. Never infer approval from agent synthesis, aggregation, reviewer recommendations, timestamps, or Context changes.

## 7. Reviewer architecture

Keep `kapisch-reviewer` as a reusable logical role. Define lenses in a concise portable contract, each with required context, target, criteria, report format, and escalation conditions:

- Intent and requirements completeness
- Research and documentation quality
- Architecture, ADRs, API/event contracts, and non-functional requirements
- Decision readiness (options, evidence, risks, assumptions, unresolved questions)
- Code quality and maintainability
- Security, permissions, privacy, and applicable isolation boundaries
- Test strategy, coverage, and verification evidence
- Operations, recovery, audit, and deployment readiness

Apply relevant lenses before important human decisions as well as after implementation. Preserve existing useful review/risk checks where they fit; do not create one-off review subsystems. Reports state evidence, findings, confidence, unresolved issues, recommendation, and escalation. Human approval remains a separate explicit decision.

The owner confirms that `kapisch-reviewer` is advisory: it reports findings and recommendations, never human approval. A WorkOrder may require successful passing of specified review lenses before dependent tasks proceed. A pass is evidence that the lens criteria were met, not authorization. Where WorkOrder policy permits an allowable finding/risk exception, the human may explicitly accept it and authorize proceeding within the approved scope; preserve the original verdict and record the exception separately as a HumanDecision referencing that report/verdict. Do not rewrite a failed verdict as pass or create a separate review-approval subsystem. Generic risk acceptance cannot bypass normative or security restrictions. After a report, the human decides what findings to take, approve, fix, or accept. A required non-pass keeps dependent work blocked. Human-directed in-scope remediation may proceed, but authorizes only the remediation task; dependent tasks stay blocked until a new review report meets the required criteria or a separate permitted HumanDecision exception authorizes proceeding. Pending, interrupted, or completed-but-still-failing remediation remains blocked. The coordinator may add human-directed tasks within the approved scope without per-task approval, but must not start an autonomous or unbounded review→fix→review loop. When recommendations would expand scope, stop, inform the human, conduct additional discussion/research as needed, and obtain approval before expanding. Do not add a database or loop-management subsystem for this. Current V3 separately models reviewer approval (`Gate.APPROVAL`) and human decisions; the target must explicitly replace the reviewer's authority semantics rather than treat reviewer output as human approval.

Pi has a known enforcement limit: `harnesses/pi/README.md` says reviewer/researcher receive Bash and pi-subagents cannot constrain Bash commands. The adapter must report read-only review as unsupported unless a genuinely enforced mutation-free path exists (for example, no arbitrary Bash or an enforced read-only sandbox). A role prompt or tool list alone is not proof. Codex is a candidate first adapter due the existing package, but its relevant enforcement must also be verified rather than assumed.

## 8. Harness adapters and package boundary

Keep the core contracts for Context, WorkOrder, HumanDecision, Attempt/result, Report, and Outcome harness-neutral. A thin adapter maps a generic attempt ID to host handles and implements only the concrete operations the host supports: capability reporting, start, collect, and optional status/resume/stop. Return a small fixed capability set such as sub-agent dispatch, parallelism, isolation, status/resume, enforced write scope, and read-only review. Values are `supported`, `unsupported`, or `unknown` with a reason. Unsupported required capabilities block or trigger an explicit human re-scope; do not silently fake them.

The same portable WorkOrder and authority rules apply to every adapter. Repository isolation is task-level and required only when a task needs a mutable isolated checkout; read-only research/review may share a read-only repository view. Acceptance runs the WorkOrder through one real adapter and one lightweight test adapter and compares logical state, evidence, decisions, reports, and outcomes. The test adapter validates the boundary, not the real host's security or execution guarantees.

This approved direction does not assume current code is useless. It reuses useful policy, role, reviewer, packaging, and host functionality where they fit; it rejects old execution semantics as the new product contract.

## 11. Acceptance scenarios and roadmap

### Acceptance scenarios

1. **Single-task SDLC flow:** Start from existing Context and sources; create a scoped WorkOrder; run an attempt with a unique output location and use a task-level worktree only if mutable repository isolation is needed; collect verification and review evidence; obtain an explicit human decision where required; write an Outcome. If work reaches release, prepare and review the deployment decision but leave execution to the target platform under explicit human authorization; bring verified operational feedback into the next Context. No agent recommendation or status label can substitute for approval.
2. **Human consultation and decision applicability:** Avoid a question already answered in the repository. Surface one material unknown with evidence/options/trade-offs. Answer Q1 against Context C0; persist immutable Decision D1 bound to Q1, relevant governing inputs, subject, and scope. Publish Context C1 carrying the answer and D1 reference; propagation does not stale D1 or create a cycle. Add unrelated context and verify applicability remains. Change a substantive governing requirement and verify reassessment; obtain a new decision only if D1 no longer covers the work. Approve DAG W0 for scope S containing tasks A and B; verify both tasks proceed without per-task approvals and a later task within S can cite W0's approval. Verify work outside S blocks pending additional human approval. Preserve old decisions and prohibit inference from agent/reviewer/timestamp/context changes.
3. **Multi-task DAG:** Approve required tasks A and B with their dependency in the DAG, without enumerating attempts. Dispatch A, record a failed attempt, then retry A with a fresh attempt ID without changing/reapproving the DAG or seeking new human approval. Verify aggregation covers required tasks through valid selected outcomes while preserving failed, superseded, late, or conflicting attempt references; missing/invalid outcomes block dependent work. Each worker has a unique output path; read-only workers may share a read-only repository view, and mutable work uses one task-level worktree when needed.
4. **Independent review:** Run `kapisch-reviewer` with requested lenses. Verify the immutable report preserves its original failed verdict. Where WorkOrder policy permits, the human can record a separate in-scope exception/authorization referencing that verdict and continue without rewriting it; generic risk acceptance cannot bypass normative or security restrictions. Verify a prohibited exception blocks. A human-directed pending fix, an interrupted/resumed fix, and a completed fix that still fails must each leave dependent tasks blocked; only a new passing review report or a permitted separate HumanDecision exception releases the gate. Verify an in-scope fix does not need per-task approval and no autonomous unbounded review/fix loop or separate review-approval subsystem is introduced. If review implies out-of-scope work, pause for discussion/research and explicit approval. For Pi, assert read-only capability is unsupported unless enforcement has been added and proven.
5. **Interrupted local work:** Interrupt a local attempt with partial files. Preserve its task worktree if one exists; retry the same approved task from a verified compatible checkpoint using a new attempt ID and output location, without changing/reapproving the DAG or requiring another human approval. Verify stale-input checkpoints are rejected, prior failed attempts remain referenced, and no shared/user-owned directory is reset or cleaned.
6. **Ambiguous remote side effect:** Simulate an uncertain push/deploy/API write. Verify retry stays blocked until an authoritative operation/target query or an explicit scoped human decision; a missing agent result is not treated as proof of non-occurrence.
7. **Harness portability:** Run the same WorkOrder through a real adapter and the test adapter. Compare logical status, authority, decisions, evidence refs, reports, and Outcome. Exercise a missing capability and verify it is surfaced, not silently emulated.
8. **Fresh-session context preservation:** Restart the controller with no conversational/process memory. Reconstruct current work, open questions, decisions, result coverage, and next valid action from the persisted artifacts and adapter-owned metadata. No implicit context may be required.
9. **Audience neutrality:** Compare default plain output with an explicitly selected presentation style. The wording may differ, but normalized facts, options, recommendations' evidence, references, decisions, and authority are identical.
10. **Packaging and cutover:** Before removing old paths, install/smoke-test reviewer availability and invocation for each supported package, validate the new-format entrypoint, and check generated artifacts. Do not test or promise old-format migration as a compatibility goal.
