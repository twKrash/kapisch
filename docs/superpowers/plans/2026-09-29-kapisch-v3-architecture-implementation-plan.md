# KAPISCH v3 Architecture Implementation Plan

**Status:** Accepted for implementation in a new session; no production implementation occurs in this acceptance session.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **Planning document only:** no step authorizes implementation, commits, installation, tagging, or release in the current session. The Kapisch self-hosting boundary forbids Kapisch-managed development of Kapisch.

**Goal:** Produce a host-neutral, independently validated v3 protocol and CoreBundle, then two independently compiled host adapters, without migrating or silently resuming v2 authority.

**Architecture:** Python 3.11 stdlib-only `kapisch_core` owns policy and versioned authority; one canonical role/workflow corpus compiles to exact immutable CoreBundle bytes. A fake adapter proves the inversion before Codex/Pi integrations; host adapters consume the bundle and retain their own transport/runtime policy. New `.kapisch/v3` state never shares authority with v2.

**Tech Stack:** Python 3.11 stdlib and `unittest`, JSON/Markdown, Git CLI for semantic repository facts, Bun/TypeScript for Pi projection and tests; no additional runtime dependency without separate justification.

**Spec:** `docs/superpowers/specs/2026-09-29-kapisch-v3-architecture-design.md` (accepted architecture contract).

## Global constraints and safe-cutover rule

- Protocol `3`, new `.kapisch/v3/runs/<run_id>/`, exact retained `.kapisch/v3/bundles/<sha256>.json`; v2 `.kapisch/runs/*` and `.planning/*` are refused, never converted. A run has exactly one owning protocol, selected at creation; never fall back from a failed v3 gate into v2.
- Core is stdlib-only, has no Codex/Pi import, path, provider ID, TOML field, or marketplace convention in domain/schema/bundle. Adapters may depend on core/bundle but not each other. `tooling/` may know both; tests can exercise all.
- `Role`, `Workflow`, `Stage`, `Gate`, `AuthorityGrant`, `Risk`, `ExecutionClass`, `LogicalTier`, `ReviewDepth`, `ReviewScope`, `CapabilityEffect`, `Transition`, `EvidenceRef` and run/attempt records are core-owned; `balanced|quality|budget` and provider/model settings are adapter-owned. Six complete role contracts have one handwritten v3 owner each.
- A Python 3.11 conformant validator gates **all** authoritative decisions, including graph-free task review and accepted advisory/plan gates; future implementations conform to JSON/protocol scenarios, not Python signatures. Non-authoritative advisory and findings-only standalone review may omit validator. Exit 0 does not itself establish independent judgment or readiness.
- Host/adapter-produced inbound-human receipt or explicitly externally supplied, byte-bound human approval artifact is mandatory for each authoritative human gate; only host-observed fields have machine-observable origin, not cryptographic authorship. Accepted snapshots are separate immutable canonical JSON; mutable state stores checked references. Complete pre/post/current semantic repository fingerprints and independent fresh whole-branch review precede final readiness.
- Persist `dispatch-uncertain` before calling an adapter; never redispatch an unresolved operation. One writer, bounded history, atomically published state; telemetry/controller view are never authority. Unknown capability or Pi shell-only reviewer blocks authoritative `approve`/`ready`.
- Stage 1–11 produce **inactive v3 artifacts/tests only**. Keep the existing `plugins/kapisch/` Codex v2 plugin and `harnesses/pi/` live package v2-only until Stage 12's explicit cutover PR. Do not regenerate live agents or change runtime routing in preparatory PRs. **Before Stage 12 can merge or activate v3**, separately authorized preservation must have produced a pinned, maintained v2 distribution and verified it can still validate a representative v2 run; if authorization/preservation is unavailable, stop at Stage 11 with v2 active. Branch/tag creation, installation and release each require later human authorization. Rollback before cutover is simply leaving v2 active; after cutover select the verified complete v2 distribution or a corrected v3 build, never a mixed-protocol fallback. Each internal task's **commit boundary** identifies a future task-scoped commit for a separately authorized execution workflow; none authorizes a commit in this planning session.

### Temporal assertions and staged supersession

Some earlier-stage tests intentionally encode temporary absence, blocking, or inactivity conditions that a later approved stage is designed to supersede.

When a later task intentionally changes such a condition:

1. identify the earlier assertion before implementation;
2. include its owning test file in the later task's approved scope;
3. retire or replace the obsolete assertion in the same task;
4. move the durable replacement assertion to the test/module that owns the final responsibility;
5. preserve genuinely permanent invariants unchanged.

Do not keep contradictory tests merely because they originated in an earlier accepted stage, and do not silently weaken permanent invariants under the label of supersession.

Examples include:

- Stage 1 no CLI → Stage 4.4 installed CLI;
- pre-Stage-7 unsupported dispatch → Stage 7 approved dispatch;
- unsupported gates that become supported only in their owning later stage;
- inactive staged v3 → explicit Stage 12 activation.

### Implementation quality and decomposition

Applies to every remaining implementation task. Each production module has one primary reason to change; public modules may be small facades. Keep filesystem/subprocess discovery, byte parsing/serialization, structural validation, policy/authority decisions, orchestration/state transitions, external effects, and presentation/telemetry separate. Functions perform one coherent operation at one abstraction level: split discovery, parsing, indexing, ownership/chronology validation, mutation, and effects into explicit phases. Prefer deterministic pure helpers and isolate I/O at clear boundaries.

High-level orchestration depends on focused lower-level helpers; avoid circular imports and keep host-specific dependencies out of core. Pass the narrowest immutable data required; use private frozen records/indexes when they clarify context instead of passing complete `RunState`, `CoreBundle`, repository objects, or broad context. Share parsing, containment, binding, canonicalization, and indexing only where semantics and ownership are genuinely identical.

When an independent responsibility appears, prefer a focused private module over enlarging a central module/function. Preserve public interfaces as small facades. Do not add speculative factories, inheritance, registries, plugin systems, or generic frameworks. Avoid inheritance unless an existing multi-implementation boundary needs it; any introduced `Protocol`/ABC/interchangeable implementation requires shared contract tests proving substitutability.

Review triggers (not runtime limits): reassess modules near 350 lines and functions near 60 lines; modules above 500 lines or functions above 100 lines require explicit task-report justification or decomposition before final review. Do not split mechanically to meet counts. At completion, report production line counts for changed/new modules, the largest function and approximate size, threshold crossings, and why any retained crossing is coherent.

For bounded histories, inventories, graphs, manifests, or repository facts, build one deterministic derived index when multiple phases need repeated lookups; avoid repeated full scans. A task's file list defines approved scope, not a mandate for a monolith. If SRP requires additional private files, stop before expanding scope, amend this plan with responsibility/file ownership, preserve public interfaces and semantics, then continue under this accepted clarification. Apply this contract to Stages 8–10 without restructuring them for uniformity; amend those stages only if a concrete responsibility collision appears.

## Review focus: extra failure inputs to pin in the owning stage

1. Unicode/newline/non-UTF-8 Git paths and symlink escape → byte-exact path encoding, contained reads and safe failure (Stages 4, 6).
2. Unborn HEAD, unmerged index, submodules and files changing during inspection → explicit blocked authority rather than a partial/guessed fingerprint (Stage 6).
3. Missing Python or corrupt/same-version-different retained bundle on a graph-free gate → diagnostic and blocked approval without trying distribution copy (Stage 4; adapter probes in Stages 8–9).
4. Duplicate host-local inbound-action ID **within one session**, retargeted receipt or controller-generated approval record mislabeled as an external artifact → reject before acceptance (Stage 5). IDs from different sessions may coincide; filesystem authorship is not provable.
5. Reviewer launches with injected tool/extension, forbidden write despite a read-only prompt, or unavailable host proof → denied write, `unknown` capability and findings-only, never approval (Stage 9).

##### 4.0.1 Evidence and alternatives

Governing evidence: accepted design §§9–13, 16–17 and 27.5–9; Stage 2 `core/schemas/v3/{stage,run,invocation}.json`; Stage 1 `core/kapisch_core/domain.py`; Stage 3 `tooling/conformance/adapter.py` and `tests/conformance/fake_adapter.py`. Current schemas are closed. `stage.json` calls `stage_id` a **stable stage-attempt identity**; `run.history` contains stage records; invocation requires `run_id`, `operation_id`, `stage_id`, `role`, `request_digest` and `status`. The private domain `AttemptRecord` already has an `attempt_id`. Stage 3 currently implements compile, human observation and static evaluation only: it does **not** implement dispatch/reconciliation or prove operation recovery. Architecture §12 and Stage 7 own that future private adapter extension; do not pretend it already exists.

| Interpretation                                                                                 | Correctness / recovery                                                                                                                           | Complexity / compatibility                                                                                                                                                                                        | Decision                                                          |
| ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| A: `stage_id` is a stable logical stage occurrence; each execution has a distinct `attempt_id` | Sound only if every invocation, result and retry binds both the occurrence and exact attempt; `stage_id` alone would be ambiguous after a retry. | Adds another identity level and parent mapping; changes current schema meaning and requires new attempt fields in stage/invocation and every consumer. Milestone `node_id` already supplies stable work identity. | Not recommended. Do not silently reinterpret existing bytes as A. |
| B: `stage_id` identifies one stage attempt; `attempt_id` is the exact domain alias of that ID  | Every invocation resolves directly to its single attempt; retries use new stage IDs, resume/reconciliation preserve them.                        | Preserves current description and invocation field. B means `attempt_id == stage_id` exactly, not two separately generated IDs. The domain may name this value `attempt_id`; JSON uses **only `stage_id`**. Neither an optional second JSON field nor a fabricated default is permitted. Mapping is a documented lossless field-name mapping at the private domain/serialization boundary, never a migration of old records. `stage_kind` is classification, not identity, parent, ordering or authority.

##### 4.0.2 Proposed identity matrix

All references are qualified by the owning `run_id` even where the containing run supplies it. IDs are opaque strings; consumers must not infer scope, authority, status or history order from their spelling. Same string in another run denotes a different attempt.                                                                                                                                                                                         | Exactly one parent run; zero or one parent milestone node; zero or one adapter operation; zero or one retry predecessor. Multiple immutable history observations may reference the same attempt.                                                                           |
| `attempt_id`   | The same controller-produced value as `stage_id`; no separate generation point.                                                                                                                                                                                                                             | Exactly the same uniqueness and lifetime.                                                                                                                                                                                                                                                                                                                                   | Private `AttemptRecord.attempt_id` serializes to `stage_id`. A separately supplied/mismatching wire `attempt_id` is rejected as an unknown field.                                                                                                                          |
| `node_id`      | Controller generates `n-` + 32 lowercase UUID hex digits when defining one milestone work node in the proposed immutable graph, **before** human approval of the plan/graph. Human approves the byte-bound definition, not a new ID.                                                                        | Unique within one run's graph and retained through retries/resume. Its binding to the exact scope document/digest, dependency definition and approved graph/plan version is permanent. It must never be rebound; execution-changing replacement requirements/dependencies need new node identity and newly approved authority. Adapter echoes it; adapter never substitutes its provider invocation ID. | Unique across runs in the **repository authority namespace** and in the adapter's applicable operation lookup namespace. Retained permanently with request/observations; never reused, including after failure or a proven non-dispatch.                                                                                                                                    | Exactly one `(run_id, stage_id)` and one immutable request digest plus selected adapter identity/lookup context. One attempt has at most one operation; one operation has zero or more read-only observations but at most one accepted terminal outcome.                   |

Uniqueness is an enforced namespace rule, not a claim that UUID randomness proves global uniqueness. Repository publication rejects an already-owned operation ID; an adapter unable to preserve unambiguous lookup/binding in its backend must report reconciliation unavailable. Different repositories do not share authority; repository/adapter lookup context is persisted with the request so an observation from another context cannot satisfy this operation. Provider/session IDs are separately factual adapter evidence, not aliases for core IDs.

**Strict durable operation reservation order (future Stage 4.2 storage primitive, consumed by Stage 7):** all steps below are mandatory and ordered. Step N+1 cannot begin until step N's durable publication and required checks have succeeded; a partially completed or indeterminate write is not success. No adapter call occurs within steps 1–3.

1. **Persist request and prerequisite immutable evidence.** After validating the existing run/attempt, exact retained bundle and current authority, publish the full canonical adapter packet and all immutable input evidence it cites (assignment, scope, approved authority, repository/context evidence required by the gate). The packet includes the proposed operation ID and exact adapter lookup binding. Compute `request_digest` from its exact bytes without a self-referential digest field; reread/check every reference. Receipt/result/verification produced by the operation are future evidence, not fabricated prerequisites. Incomplete, missing, corrupt or non-durable input publication blocks reservation.
2. **Atomically reserve the operation and its entire binding.** Under the repository-scoped publication lock, inspect all retained run invocation/history ownership, reject collision or unreadable ownership, then atomically publish the immutable planned invocation at `.kapisch/v3/runs/<run_id>/invocations/<operation_id>/planned.json`. This single reservation fact binds `operation_id`, `run_id`, `stage_id` (the attempt), `role`, `request_digest`, exact request `{path,sha256}` and `adapter_binding` `{adapter_id,lookup_context}`; the latter contains the exact nonempty adapter lookup namespace/context token persisted in the packet, not an inferred current session. Publication is no-overwrite and all fields become visible/durable together; no ID-only intermediate reservation is valid. `request.sha256` must equal `request_digest`, and resolved packet IDs/adapter fields must match the reservation. This planned invocation is the reservation, **not** a new recovery journal or mutable index.
3. **Publish durable uncertainty.** After reservation success, publish its immutable `dispatch-uncertain` invocation fact, then atomically replace durable run state with the next observation citing exact packet, reservation, uncertain fact and prerequisite evidence. Check expected revision, immutable history prefix, original bindings, invocation inventory and authority freshness. Reservation and run-state publication are deliberately **not** one cross-file transaction; an intermediate reservation or uncertain fact must remain discoverable and fail closed as described below. Both the immutable uncertain fact and its state pointer must be durably published before proceeding.
4. **Invoke the adapter once.** Only the original writer that completed all preceding steps successfully may issue this call with the exact reserved packet/operation. Locks are released before calling the adapter; run ownership still excludes another dispatcher. A restart after step 3 is recovery, not permission to invoke: the outcome is uncertain even if no call occurred. Persist factual receipt/result later without changing reservation or request.

Whenever both locks are needed, acquire repository lock before run lock. Run revision checks alone cannot reserve a repository-wide ID. Inspection failure, corrupt/unreadable/symlinked ownership, changed binding, collision, durability error or uncertain publication acknowledgment blocks; never assume absence or proceed to the next step. An existing exact-owner reservation is recognized for read-only recovery, **not** treated as a new reservation success that permits redispatch. The reservation stays occupied if any later publication fails or the process crashes. Abandoned, failed, never-started and completed runs retain reservation facts permanently; no supported automatic cleanup releases an operation ID. Stage 4.2 owns ordered immutable publication, atomic reservation, cross-run collision and durability/fault tests; Stage 7 owns enforcement at adapter dispatch/reconciliation boundaries.

##### 4.0.3 Allowed relationships and append-only history

1. Run creation owns `run_id`, `workflow` and exact retained `bundle_digest`; none changes on resume or a retry. An attempt's creation fact owns its `stage_id`, `stage_kind`, `role`, `scope_digest`, optional `node_id`, and optional `retry_of_stage_id`. These fields cannot be rebound in later observations. Changing kind, assignment role or scope requires a new attempt; stronger-role corrective work is not silently relabeled as a retry of a differently assigned attempt.
2. History is a bounded **ordered list of immutable observations of attempts**, not a mutable one-row-per-attempt table and not a separate event-log file. `sequence` is the zero-based contiguous position in `run.history`, unique across that run, not the attempt ID or retry count. First occurrence of a stage ID is exactly one `planned` creation fact. Later occurrences are explicitly observations of that same attempt, with identical creation fields, new sequence and only admissible progress/additional checked evidence. Identical duplicate observations, duplicate creation, missing prefix/gaps, reordered rows, conflicting bindings, evidence removal and changed earlier rows are rejected by publication-time prefix comparison and by cold structural validation where the violation is observable. Cold structural validation alone cannot detect restoration of an internally consistent earlier snapshot; the dispatch-veto rule below is mandatory. Derived latest status does not replace or truncate earlier rows. Terminal attempt records and accepted terminal results never change.
3. Evidence references in an observation are cumulative: all previously cited references remain byte-identical; only independently justified new references may be added. Exact producer artifacts are published immutably before the state observation that cites them. Each operation's planned invocation, uncertain marker, receipt/result and verification are distinct immutable facts/files, not one invocation file rewritten in place. `invocation.status` describes that particular fact, while the attempt's effective status comes from its ordered observations. No new status vocabulary is proposed here.
4. A retry creation has a new stage ID and `retry_of_stage_id` naming the **latest** earlier eligible attempt in its chain. It preserves kind, role, node membership/absence and bound scope. Only one direct retry successor is permitted; predecessor must be known failed, blocked-before-dispatch, or interrupted with safely resolved/quiescent operation evidence. No self-reference, forward reference, branching/cyclic retry, cross-run parent or retry of completed verified work. Root/new independent attempts omit the predecessor; absent and JSON null are not interchangeable.
5. Task, advisory and review workflows contain **no graph, node definitions, dependencies or `node_id`**, including retries and authoritative review. Their ordering and attempt grouping come from history, scope and explicit retry links. A task's separate implement/review/gate attempts are not graph nodes or retries of one another. Standalone findings-only/non-authoritative work still need not create durable authority state.
6. Milestone state cites one immutable graph by path/digest. Graph document has closed fields `protocol_version`, `run_id`, `plan_id`, `nodes`; each node has closed fields `node_id`, `scope` (contained immutable `{path,sha256}` reference), `depends_on` (unique node IDs). Nodes and their dependency targets are defined before execution, with no cycles or missing targets. Each scope reference resolves exact canonical JSON bytes with closed fields `protocol_version`, `run_id`, `node_id`, `requirements` (complete normative work/requirements text, not merely a label or an unresolved prose pointer). Controller publishes this document at `scopes/<node_id>.json` before publishing graph bytes at `graphs/<plan_id>.json`, both relative to the run directory. `stage.scope_digest` must equal the node's `scope.sha256`; scope document run/node IDs must match the graph owner/node. Validator reads contained scope bytes and checks digest and closed schema, not just equal digest strings. Human-approved plan binds this exact graph path/digest; graph contains `plan_id`, **not** a reciprocal plan-byte digest (no circular hashing). State and graph plan IDs must agree with `approved_plan`. **Immutable node authority binding:** validation resolves the full `(run_id, node_id, scope path/digest, graph path/digest, approved plan ID/path/digest)` tuple and the human evidence approving those plan bytes. Attempt creation evidence (existing assignment/request or gate artifact, not a second mutable node registry) binds this exact tuple before consumption; later observations, retries, results and node-completion evidence preserve it. Matching `node_id` and scope digest without the exact approved graph/plan version is insufficient. Neither a state-pointer change nor a later approval may rebind an existing node to another scope document or dependency definition.

   Any execution-relevant change to requirements, scope bytes, graph/dependencies or governing plan makes the affected previously granted execution authority stale and blocks new dispatch, retry, resume-as-execution and node-completion/readiness claims until explicitly re-evaluated and freshly approved. This includes dependency-only changes even when node scope bytes are unchanged. Detect staleness through retained byte bindings and current governing-authority checks; no caller assurance substitutes for them. Record the blocking/staleness observation append-only; do not erase earlier approvals, mutate historical node refs or reinterpret old evidence as proof for a new version. Historical approvals remain historical facts, not current execution permission. Replacing the approved graph/plan in an execution run is not a resume; the proposed replacement uses a new run, new identities for changed node definitions and newly approved scope/graph/plan authority. Completed verified work is preserved and never automatically replayed as a consequence of authority invalidation.

7. Milestone node-scoped attempts carry `node_id` and match the approved node scope. Run-wide milestone attempts explicitly bind run-wide scope and omit `node_id` (e.g. plan gate or whole-branch final); a milestone `implement` attempt always requires a node. Node-less attempts cannot complete a node or bypass dependencies. A node may own implementation, local verification/review/gate attempts and retries; a node is not complete merely because one attempt's operation finished. Stage 7 freezes the exact node-completion and allowed lifecycle edges against required verification/reviewer/human evidence; it cannot change these relationships. At most one active dispatched operation per run; graph order never permits concurrent writers.
8. A local controller gate/check can have zero operations. Any adapter child dispatch, including read-only research/review, has exactly one operation linked to an existing attempt. Invocation `(run_id, stage_id, role)` must resolve to that attempt; its request binds matching scope/node and bundle. No implicit node/stage creation from receipt/result and no second operation under an existing attempt. A separate final review is a new final attempt/operation, never a renamed iteration review.

These rules permit repeated **references** to an existing ID, not duplicate creation or ambiguous ownership. Cold validation uses current history, cited artifacts and the contained invocation-fact inventory below; optional previous-state comparison provides extra tamper detection but is not required for process-crash recovery. Hashes and this ordering do not prove authorship or defeat a privileged writer that fabricates an entire history. Bounds must fail closed rather than dropping a history prefix to make a run fit.

**Cold dispatch veto and fault boundary:** before any first-dispatch authorization or resume, storage/validation inspects the run's complete contained `invocations/` namespace, including unreferenced immutable invocation/receipt/result/verification facts. An uncertain-or-later fact absent from current history, **any reservation not cited with its exact binding in current validated state** (even when its owning attempt is present), missing/unreadable state, an unreadable/malformed fact, or inconsistent ownership blocks dispatch and authoritative completion. Such orphan evidence is **safety-veto evidence only**: it never auto-accepts a result, completes an attempt, invents missing rows or supplies affirmative gate authority. A rollback to a valid planned-state prefix therefore cannot redispatch O1 if its later uncertain/result facts remain. Stage 7 may explicitly reconcile O1 read-only and restore checked references under the original IDs; it may not guess a lost history suffix. **Orphan-reservation recovery:** inspect every retained `invocations/<operation_id>/planned.json` regardless of state references. A successfully published reservation with absent/failed/rolled-back state publication is discoverable by this inventory and vetoes dispatch and new retry. Validate its entire binding and immutable inputs, then ask the original adapter/context for a reliable read-only observation of that exact operation; missing state or receipt is never evidence of non-dispatch. Matching completed outcome may be adopted only with reconstructible producer order and verification. A reliable never-started or failed/quiescent observation may close the original attempt and permit an explicitly authorized fresh attempt/operation; it never permits sending the reserved operation again. Unknown, unavailable or mismatched observation remains blocked, with reservation intact. If binding/producer order cannot be reconstructed from persisted facts, remain blocked. Immutable uncertain facts must be published before their state pointer and before the call, so a crash after file publication but before state publication conservatively blocks even if no call occurred.

Supported recovery faults are process crashes and atomic state-publication failures with published immutable authority/evidence retained. Coherent rollback/deletion of **both** state and all corresponding immutable invocation/reservation evidence, filesystem durability loss and privileged fabrication are not detectable from these files alone; they are outside this protocol's fault guarantee. Do not claim detection of arbitrary valid-prefix rollback or authority-storage deletion. Storage requires durable immutable publication before durable state replacement and dispatch; unsupported filesystem guarantees block. No restoration tooling may silently reactivate an old snapshot as a new first-dispatch state. This is not an external anti-rollback ledger or a replay engine; it is conservative inspection of the already required operation facts.

Atomic reservation and state replacement have separate durable commit points. Failed or indeterminate acknowledgments stop the writer; cold recovery examines retained facts rather than its remembered return value.

##### 4.0.5 Concrete traces (illustrative shorthand, not accepted fixtures)

`S1`, `N1`, `O1` below stand for distinct correctly formatted IDs. Each arrow appends a new immutable observation with the next contiguous sequence. Actual packet/result IDs, scope and bundle digests must be present and equal; labels never substitute for them.

- **Graph-free task:** `(S1, implement, no node)` planned → `(S1, O1)` uncertain → matching terminal result + verification → S1 complete. Independent review creates `(S2, review, no node, O2)` with its own bound invocation/result. A local gate `(S3, gate, no node)` may have no operation. No graph/dependencies/node IDs are fabricated.
- **Task retry:** S1/O1 safely observed failed and quiescent → human/authority/effect checks permit retry → `(S4, implement, retry_of=S1, no node, O4)` planned → uncertain → observed and verified complete. S1's historical rows never change; S4 is not S1 resumed. New review targets S4's actual result/current scope, not stale S2 evidence.
- **Milestone:** graph `(N1 scope=D1; N2 scope=D2 depends_on=[N1])` is byte-bound by approved plan. N1's implement attempt S1/O1 and review attempt S2/O2 both name N1 and D1. If S1 safely fails, retry S4/O4 still names N1/D1. N2 attempts are barred until N1's required node-completion evidence validates. Whole-branch final S5/O5 is run-wide, omits node ID and has fresh independent context; completed N1 work is not rerun at final/resume.
- **Crash before/after dispatch:** persist S1 creation, exact O1 packet and required immutable inputs → atomically reserve complete O1/run/S1/request/adapter bindings → durably publish S1/O1 uncertain fact and state pointer → crash either immediately before the adapter call or after it. Both recovered states are treated identically: no new S/O, no dispatch. A reservation surviving failed state publication is an independently discoverable veto, including when S1's planned row survives. Matching read-only reconciliation of O1 may append existing result and verification and complete S1; unreliable/missing observation stays blocked.
- **Crash after immutable result but before state pointer:** orphan result O1 is not authority simply because a file exists. Resume validates existing uncertain S1/O1; explicit matching reconciliation verifies/adopts the exact producer result by appending checked references, or remains blocked. No orphan creates a new attempt/operation.
- **Valid-prefix rollback:** restore the exact planned S1/O1 snapshot after either uncertain dispatch or verified completion, leaving immutable O1 facts intact. Contiguous numbering alone appears valid, but cold inventory finds uncertain-or-later facts absent from history and vetoes dispatch/completion. Explicit read-only O1 reconciliation may recover checked bindings; otherwise block. Joint deletion/rollback of all those facts is expressly outside the supported fault model.
- **Cross-run collision:** two runs propose identical O1 under their independent writer locks. Repository-scoped reservation serialization permits at most one owning planned fact; the other publication fails before dispatch. Restart/failure/abandonment never frees O1.
- **Resume after completion:** current state already includes S1/O1 completion and verification → independently validate persisted identity/evidence and current governing/repository facts → preserve S1/O1; continue only an eligible later attempt. Deleted controller view and missing chat cannot trigger S1/O1 dispatch.

#### Track B contract amendments (approved before implementation)

The schema-preserving recommendations from the independent plan review are adopted for Stage 6.1–6.4:

- Tracked worktree modes are canonicalized as `100644` for a non-executable regular file, `100755` when the owner-execute bit is set, and `120000` for a symlink whose digest is the raw link-target bytes. A deletion uses `000000` and has no digest. Other permission bits, ownership and timestamps are not identity. Git index modes remain captured and validated separately.
- Explicitly included untracked evidence is regular-file-only and byte-only under the existing schema. Included symlinks, directories, devices and FIFOs are rejected; untracked executable mode is intentionally not bound. Unincluded entries are inventory-only and carry no content or mode digest.
- The required `git ls-files --others --exclude-standard -z` inventory is instance-dependent on the effective repository/local/global ignore configuration. Equal semantic inputs, including effective ignore policy, produce equal canonical bytes; identical committed checkouts are not promised identical inventories across differing host policies.
- The tracked worktree universe is the unique current index-path set. HEAD-only paths after staged deletion have no tracked worktree entry; a retained file is represented through untracked inventory when reported. Staged additions are tracked immediately. Nonzero stages are parsed but final composition rejects them. Skip-worktree/sparse checkout/sparse-index states and all current-index gitlinks are unsupported and fail closed; capture must observe the relevant flags/configuration across both passes.

These decisions preserve the existing repository-state schema and do not authorize Stage 6.5, validator, adapter, telemetry, or cutover changes. The implementation must amend tests and module contracts to enforce them before any green-claim.
